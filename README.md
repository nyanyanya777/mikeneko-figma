# mikeneko-figma — Figma作業のためのClaude Codeスキル群

Figmaにおけるデザインやデザインシステムの作業を、Claude Codeに任せるための自作スキル群です。
実務で失敗するたびにルールを追加してきたもので、大半の条項の背景には実際の失敗体験があります。

## これは何を解決するか

Figmaでの作業をAIに任せると、だいたい同じようなパターンで失敗します。

- デザインシステムに実体があるにもかかわらず、生のフレームを使って見た目だけ似せたものを作成する
- 検索にヒットしなかっただけで「そのようなコンポーネントは存在しない」と断定し、新しく作成してしまう
- スクリーンショットが一致したという理由だけで「完成」と報告してくる
- 「全ページ」と指示したにもかかわらず、作業中の1ページだけを修正して完了扱いにする
- 頼んでいないタブや列、編集操作などを「この種の画面には通常存在するから」と勝手に追加する
- 画面を「作成方法の選択→入力→確認」のようなウィザード形式にしてしまい、扱う対象（オブジェクト）が見えなくなる
- 洗い出した概念をすべてそのまま画面の箱にしてしまい、選択肢の値や操作までオブジェクトとして扱ってしまう

このスキル群は、こうした失敗を**着手前・実装中・完了前のゲート**において構造的に防ぐことを目的としています。
単なる文章による注意書きではなく、判定できる条件として記述している点が特徴です。

## 設計の土台: OOUI とオントロジー

画面は「何のオブジェクト（名詞）の、どのビュー（一覧か詳細か）であるか」を起点に設計します（OOUI、F-OOUI-1〜5）。
動詞は画面やステップとして扱うのではなく、ビュー上のアクションとして配置します。

その前段階として、オントロジーの層を設けています。

- **オブジェクトの確定**: 洗い出した概念をすべてそのまま箱にするのではなく、画面上で1件ずつ扱うものだけをオブジェクトとして定義します。値はプロパティへ、操作はアクションへ振り分け、対応表を用いて未割り当てが0になることを確認します（F-OOUI-8）
- **関係**: オブジェクト同士の参照関係や多重度（1:1、1:N、N:N）を、画面に配置する前に宣言します（F-OOUI-6）
- **操作権限**: ロールごとに「操作可能」「閲覧のみ」「操作不可」を宣言し、画面要素の非表示や無効化に反映させます（F-OOUI-7）

設計の順序は「オブジェクト → 関係・操作権限 → ビュー」となります。
また、画面に配置する要素は、依頼者の発言（逐語）、要件文書、既存画面のいずれかに出典があるものだけに限定します（F-SRC-1）。

## 構成

```
skills/
  mikeneko-figma/          入口。ここで1問だけ判定して、作業スキルを1つだけロードする
    scripts/
      audit-structure.js    生フレーム混入・重複クラスタ・ページ構成の機械監査
      audit-ds-binding.js   色/タイポの変数バインド率の機械監査
  mikeneko-figma-rules/    共通禁止事項（F-*ルール）の唯一の正典（SOT）＋最終ゲート対応表
  figma-ds-edit/           既存のデザイン/DSファイルの編集・レビュー
  figma-component-design/  新規コンポーネントの設計、プロパティ軸の大改修
  figma-design-create/     要件からの新規画面・フロー作成
  figma-e2e-test/          画面の「体験」のE2E検証（設計は直さない、テスト専用）
  figma-modal-open-reorg/  素置きモーダルを「開いた状態」に組み直し、バリアント付きコンポーネントへ格上げ
docs/                      各ルールの根拠。なぜそのルールがあるかの実例つき
```

`skills/` 内の各 SKILL.md から、`docs/` にある該当の根拠へとリンクを張っています。
ルールの文面だけでは判断が難しい場合があるため、迷ったときは根拠のドキュメントを参照してください。

### 各スキルの中身

- **mikeneko-figma（入口）**: 依頼された作業が「既存の編集」「新しい部品」「新しい画面」「体験のテスト」のどれに該当するかを1つの質問で判定し、適切な作業スキルを1つだけ読み込みます。その際、必ず共通ルールも併せて読ませます。既存画面もデザインシステム（DS）も存在しない新規サービスの場合は、別スキル `mikeneko-design-md`（本リポジトリ未収録）へ誘導します。
- **mikeneko-figma-rules（共通ルールの正典）**: すべてのスキルに適用される F-* ルールの本文は、このファイルでのみ管理します。また、各スキルの最終ゲートとの対応表や、ルールを追加する際の規約も記載しています。
- **figma-ds-edit（既存の編集・レビュー）**: ファイルの現物の棚卸し、計画とゲートの確認、実装、そして全件レビューという手順で進めます。テキストスタイルや色変数のバインド状況、生のフレームから部品への置き換え、逆差分監査（頼んでいない要素が増えていないか）、OOUIの整合性（別のオブジェクトが混入していないか、ウィザード化していないか）、オブジェクト間の関係や操作権限の整合性、重複監査までをチェックします。
- **figma-component-design（新しい部品）**: Variant、Boolean、Text、Instance Swap のどれを軸にするか、auto-layout の HUG / FILL / FIXED の設定、スロットの出し入れ、変数やスタイルのバインド方法を決定します。軸が直交しているかの確認、全パターンのテスト、既存の使用箇所への影響確認までを完了条件とします。
- **figma-design-create（新しい画面・フロー）**: 要件の確定から着手し、新規作成する画面、改修する画面、遷移の配線リストを先に洗い出します。OOUIのビューインベントリ（どのオブジェクトのどのビューか）、オブジェクト間の関係と操作権限、ページ構成（1オブジェクトにつき1ページ）を宣言した上で作成を進め、最後に宣言内容と成果物を機械的に突き合わせます。要素の出典（依頼者の逐語、要件文書、既存画面）、既存の姉妹画面との一貫性、プロトタイプの配線までを確認します。
- **figma-e2e-test（体験のテスト）**: 利用者の目標を設定し、画面上の情報だけでその目標を達成できるかを、盲目のウォークスルーで検証します。行き詰まった箇所があれば、その原因をUXの欠陥、配線漏れ、不適切な文言、状態の欠落、OOUIの退行、ページ構成の問題のいずれかに切り分けて報告します。このスキルでは設計の修正は行わず、修正作業は `figma-ds-edit` や `figma-design-create` へ引き継ぎます。
- **figma-modal-open-reorg（モーダルの整理）**: 画面上に無造作に置かれたモーダルを、「親画面＋背景の暗幕＋中央ダイアログ」という「開いた状態」の構造に組み直します。繰り返し出現するモーダルについては、バリアント付きのコンポーネントへ格上げします。
- **scripts/**: `audit-structure.js` は生のフレームの混入、auto-layout の適用状況、重複クラスタ、所属ページについて監査します。`audit-ds-binding.js` は色やタイポグラフィの変数バインド率を、それぞれFigma上で機械的に監査します。

### 共通ルール（F-*）の系統

| 系統 | 何を止めるか |
|---|---|
| F-STR | Spacer の空フレーム、auto-layout が適用されていないコンテナ、場当たり的な線の描画 |
| F-CMP | アイコンが指定されていないアイコンボタン、手描きによる部品の偽装、マスターコンポーネントの直接編集、強調を目的とした fill や stroke の書き換え、完成フレーム内に残存する部品化されていないスタイル付き要素、同じ構造を複製したままの放置（2つ目のコピーを作成した時点で部品化する）、部品化に関する機械監査を通さないままの完了報告 |
| F-PLC | 根拠のない配置、指定ノード以外への複製、不在の断定、重複作成、1つの機能が複数のページに散在する状態、配置先のページを事前に特定しないままの複製、正規の手順を踏まずにルールの正典を書き換える行為 |
| F-SRC | 出典のない要素の配置（依頼者の逐語、要件文書、既存画面の3つのみを出典とする）、他案件の要素の混入、「良かれと思って」の勝手な追加、明言されている要素の削除 |
| F-OOUI | オブジェクトとビューを定義しないまま画面を作成する行為、ウィザード形式への退行、値や操作をオブジェクトとして扱うこと、選択肢の取りこぼし、関係性や操作権限の宣言漏れ、洗い出した概念をそのまま箱（オブジェクト）にすること |
| F-QLT | AI特有の過剰な配色、WCAG AA 基準を満たさないコントラスト、14px 未満の文字サイズ、色を変えただけの別案の作成、生の値の直接入力、ワイヤーフレーム状態での作業終了、既存画面との不一致、業界ベンチマークの指摘事項を処理しないままの完了報告、ビジュアル判定の証跡（完了報告における verdict 行）がない状態での完了報告 |
| F-PRC | 合意形成前のビルド実行、画像を認識できないモデルへの画像再現の委譲、Figma 以外への成果物の書き出し、不自然な日本語の文言、全体を対象とする指示の勝手なスコープ縮小、URL や node-id の対象範囲の恣意的な固定、デザイン作業を委譲する際のモデルの格下げ、レビュー結果の曖昧な処理、判断を伴うレビューを決定論的な監査より先に行うこと、受け入れ条件を満たした証拠の欠落、参照元のUIを確認しないままの設計、作業スキルを経由しない直接的な書き込み |
| F-INT | 余白や揃えなどの空間に関する指示に対して、対象となるノードやプロパティを特定しないまま作業を進めること、レンダリング結果を自身で確認せずに「修正が完了した」と判断すること |

## 使い方

`skills/` 配下のフォルダ群を、Claude Code のスキルディレクトリ（`~/.claude/skills/`）に配置してください。
これにより、Figmaでの作業を開始する際に `mikeneko-figma` が自動的に起動します。各作業スキルは共通ルールである `mikeneko-figma-rules` を併せて読み込む設計となっているため、必ず7つのディレクトリをまとめて配置してください。
本スキル群は、Figma の MCP サーバーが接続されていることを前提としています。
入口となる `mikeneko-figma` は既存プロダクトの改修作業を想定しています。デザインシステムも姉妹画面もまだ存在しない新規サービスのデザインに着手する場合は、別のスキルである `mikeneko-design-md` へ誘導されますが、このスキルは本リポジトリには含まれていません。
