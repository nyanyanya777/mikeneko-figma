# mikeneko-figma — Figma作業のためのClaude Codeスキル群

Figmaでのデザインやデザインシステム構築をClaude Codeに任せるための、自作スキル群です。
実務で失敗を経験するたびにルールを追加してきたため、大半の条項に実際の失敗談という背景があります。

## これは何を解決するか

Figmaでの作業をAIに任せると、よくあるパターンで失敗します。

- デザインシステムに実体があるのに、生のフレームを使って見た目だけ似せたものを作る
- 検索でヒットしなかっただけで「コンポーネントが存在しない」と決めつけ、新規作成してしまう
- スクリーンショットが一致したという理由だけで「完成した」と報告してくる
- 「全ページ」と指示したのに、作業中の1ページだけを修正して完了扱いにする
- 頼んでいないタブや列、編集操作などを「この手の画面には普通あるから」と勝手に追加する
- 画面を「作成方法の選択→入力→確認」のようなウィザード形式にしてしまい、対象のオブジェクトが見えなくなる
- 洗い出した概念をすべてそのまま画面上の箱にしてしまい、選択肢の値や操作までオブジェクトとして扱ってしまう

本スキル群は、こうした失敗を**着手前・実装中・完了前のゲート**で構造的に防ぐためのものです。
単なる文章での注意書きではなく、判定可能な条件として定義している点が特徴です。

## 設計の土台: OOUI とオントロジー

画面は「何のオブジェクト（名詞）の、どのビュー（一覧か詳細か）か」を起点に設計します（OOUI、F-OOUI-1〜5）。
動詞は画面やステップではなく、ビュー上のアクションとして配置します。

その前段階として、オントロジーの層を設けています。

- **オブジェクトの確定**: 洗い出した概念をすべてそのまま箱にするのではなく、画面上で1件ずつ扱うものだけをオブジェクトとして定義します。値はプロパティへ、操作はアクションへ振り分け、対応表を使って未割り当てが0件であることを確認します（F-OOUI-8）
- **関係**: オブジェクト同士の参照関係や多重度（1:1、1:N、N:N）を、画面へ配置する前に宣言します（F-OOUI-6）
- **操作権限**: ロールごとに「操作可能」「閲覧のみ」「操作不可」を宣言し、画面要素の非表示や無効化に反映します（F-OOUI-7）

設計の順序は「オブジェクト → 関係・操作権限 → ビュー」です。
また、画面に配置する要素は、依頼者の発言（逐語）、要件文書、既存画面のいずれかに出典があるものだけに絞ります（F-SRC-1）。

## 構成

```
skills/
  mikeneko-figma/          入口。ここで1問だけ判定して、作業スキルを1つだけロードする
    scripts/
      audit-structure.js    生フレーム混入・重複クラスタ・ページ構成の機械監査
      audit-ds-binding.js   色/タイポ/余白/角丸/影の変数バインド率の機械監査
  mikeneko-figma-rules/    共通禁止事項（F-*ルール）の唯一の正典（SOT）＋最終ゲート対応表
  figma-ds-edit/           既存のデザイン/DSファイルの編集・レビュー
  figma-component-design/  新規コンポーネントの設計、プロパティ軸の大改修
  figma-design-create/     要件からの新規画面・フロー作成
  figma-e2e-test/          画面の「体験」のE2E検証（設計は直さない、テスト専用）
  figma-modal-open-reorg/  素置きモーダルを「開いた状態」に組み直し、バリアント付きコンポーネントへ格上げ
docs/                      各ルールの根拠。なぜそのルールがあるかの実例つき
```

`skills/` 内の各 SKILL.md から、`docs/` にある該当の根拠へリンクを張っています。
ルールの文面だけでは判断が難しい場合があるため、迷ったときは根拠ドキュメントを参照してください。

### 各スキルの中身

- **mikeneko-figma（入口）**: 依頼された作業が「既存の編集」「新しい部品」「新しい画面」「体験のテスト」のどれに該当するかを1つの質問で判定し、適切な作業スキルを1つだけ読み込みます。その際、必ず共通ルールも併せて読み込ませます。既存画面もデザインシステム（DS）も存在しない新規サービスの場合は、別スキル `mikeneko-design-md`（本リポジトリ未収録）へ誘導します。
- **mikeneko-figma-rules（共通ルールの正典）**: すべてのスキルに適用される F-* ルールの本文は、このファイルでのみ管理します。また、各スキルの最終ゲートとの対応表や、ルールを追加する際の規約も記載しています。
- **figma-ds-edit（既存の編集・レビュー）**: ファイル現物の棚卸し、計画とゲートの確認、実装、全件レビューの手順で進めます。テキストスタイルや色変数のバインド状況、生フレームから部品への置き換え、逆差分監査（指示にない要素の追加がないか）、OOUIの整合性（別オブジェクトの混入やウィザード化がないか）、オブジェクト間の関係・操作権限の整合性、重複の監査までをチェックします。
- **figma-component-design（新しい部品）**: Variant、Boolean、Text、Instance Swap のどれを軸にするか、auto-layout の HUG / FILL / FIXED の設定、スロットの出し入れ、変数やスタイルのバインド方法を決定します。軸の直交性の確認、全パターンのテスト、既存の使用箇所への影響確認までを完了条件とします。
- **figma-design-create（新しい画面・フロー）**: 要件の確定から着手し、新規作成・改修する画面と遷移の配線リストを事前に洗い出します。OOUIのビューインベントリ（どのオブジェクトのどのビューか）、オブジェクト間の関係と操作権限、ページ構成（1オブジェクト1ページ）を宣言してから作成を進め、最後に宣言内容と成果物を機械的に突き合わせます。要素の出典（依頼者の逐語、要件文書、既存画面）、既存の姉妹画面との一貫性、プロトタイプの配線までを確認します。
- **figma-e2e-test（体験のテスト）**: 利用者の目標を設定し、画面上の情報だけでその目標を達成できるかを、盲目のウォークスルーで検証します。行き詰まった箇所があれば、その原因をUXの欠陥、配線漏れ、不適切な文言、状態の欠落、OOUIの退行、ページ構成の問題のいずれかに切り分けて報告します。このスキルでは設計の修正は行わず、修正作業は `figma-ds-edit` や `figma-design-create` へ引き継ぎます。
- **figma-modal-open-reorg（モーダルの整理）**: 画面上に無造作に置かれたモーダルを、「親画面＋背景の暗幕＋中央ダイアログ」という「開いた状態」の構造に組み直します。繰り返し出現するモーダルについては、バリアント付きのコンポーネントへ格上げします。
- **scripts/**: `audit-structure.js` は生のフレームの混入、auto-layout の適用状況、重複クラスタ、所属ページについて監査します。`audit-ds-binding.js` は色・タイポグラフィに加え、余白・角丸・影の変数バインド率を、それぞれFigma上で機械的に監査します。

### 共通ルール（F-*）の系統

| 系統 | 何を止めるか |
|---|---|
| F-STR | Spacer の空フレーム、auto-layout 未適用のコンテナ、場当たり的な線の描画 |
| F-CMP | アイコン未指定のアイコンボタン、手描きによる部品の偽装、マスターコンポーネントの直接編集、強調目的の fill や stroke の書き換え、完成フレームに残る未部品化のスタイル付き要素、同一構造を複製したままの放置（2つ目のコピー作成時点で部品化する）、部品化の機械監査を通さないままの完了報告 |
| F-PLC | 根拠のない配置、指定ノード以外への複製、不在の断定、重複作成、1つの機能が複数ページに散在する状態、配置先ページを事前特定しないままの複製、正規手順を踏まずにルール正典を書き換える行為 |
| F-SRC | 出典のない要素の配置（依頼者の逐語、要件文書、既存画面の3つのみを出典とする）、他案件要素の混入、「良かれと思って」の勝手な追加、明言されている要素の削除 |
| F-OOUI | オブジェクトとビューを定義しないまま画面を作成する行為、ウィザード形式への退行、値や操作のオブジェクト扱い、選択肢の取りこぼし、関係性や操作権限の宣言漏れ、洗い出した概念をそのまま箱（オブジェクト）にすること |
| F-QLT | AI特有の過剰な配色、WCAG AA 基準を満たさないコントラスト、14px 未満の文字サイズ、色を変えただけの別案作成、生の値の直接入力、ワイヤーフレーム状態での作業終了、既存画面との不一致、業界ベンチマーク指摘事項の未処理での完了報告、ビジュアル判定証跡（完了報告での verdict 行）がない状態での完了報告 |
| F-PRC | 合意形成前のビルド実行、画像認識不可モデルへの画像再現委譲、Figma 以外への成果物書き出し、不自然な日本語文言、全体対象指示の勝手なスコープ縮小、URL や node-id 対象範囲の恣意的な固定、デザイン作業委譲時のモデル格下げ、レビュー結果の曖昧な処理、判断を伴うレビューを決定論的監査より先に行うこと、受け入れ条件充足証拠の欠落、参照元UI未確認での設計、作業スキルを経由しない直接書き込み |
| F-INT | 余白や揃えなど空間指示に対し、対象ノードやプロパティを特定せず作業を進めること、レンダリング結果を自身で確認せず「修正完了」と判断すること |

### 見た目の質のチェック（F-QLT-6〜9）

見た目の完成度は、印象だけで判定しません。まず機械層（`audit-ds-binding.js` 等）が、色・タイポグラフィ・余白・角丸・影のバインド状況や、画面内の主要な操作要素の数といった事実を数えます。その事実とスクリーンショットを、判定役（AI 1体）に渡し、主導線が主役化されているか、平坦すぎたり装飾過剰になっていないか、既存画面と同じ言語で作られているかを、観点ごとに根拠つきで判定させます。この流れは F-QLT-6（完成度）、F-QLT-7（既存プロダクトとの一貫性）、F-QLT-8（業界ベンチマーク）、F-QLT-9（ビジュアル判定の実施証跡）の4段で構成されています。これらを強制する Stop フック類は本リポジトリに同梱していないため、フックの無い環境では強制されず、各スキルの手順として働きます。

## 使い方

`skills/` 配下のフォルダ群を、Claude Code のスキルディレクトリ（`~/.claude/skills/`）に配置してください。
配置すると、Figma での作業開始時に `mikeneko-figma` が自動起動します。各作業スキルは共通ルール `mikeneko-figma-rules` を読み込む設計のため、必ず7つのディレクトリをまとめて配置してください。
なお、本スキル群は Figma の MCP サーバー接続を前提としています。
入口となる `mikeneko-figma` は既存プロダクトの改修作業を想定しています。デザインシステムも姉妹画面もない新規サービスのデザインに着手する場合は、別スキル `mikeneko-design-md` へ誘導されますが、このスキルは本リポジトリに含まれません。
