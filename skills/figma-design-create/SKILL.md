# Figma 新規デザイン作成の作業標準

**TL;DR**: 新規画面/フロー/フレームを既存DSの上に要件から起こすときに発火。出力は《要件確定 → ビューインベントリ＋ページIA宣言 → 現物確認 → DS棚卸し → 設計＋ゲート → ユーザー一括承認 → 段階実装 → プロトタイプ配線 → 全件レビュー → 自分の目で最終確認》を経た新規デザインと配線。実行は全部サブエージェントに委譲し、**自分はマネジメント（要件確定・割当・ゲート判定・全件カバレッジ確認・完了可否）だけ**を握る。

## 適用範囲と境界

### やる / やらない
- **やる（本スキル）**: 0→1で画面/フレームを起こす作業（新規UIの設計・実装・既存フローへの配線）。
- **やらない（委譲）**: 既存frameへのテキスト追加・行追加・バリアント差し替え・トークンバインド是正等の**既存改修**は [figma-ds-edit](../../skills/figma-ds-edit/SKILL.md)。新規Component（atom/molecule）設計・property軸の大改修は [figma-component-design](../../skills/figma-component-design/SKILL.md)。体験のE2Eテストは [figma-e2e-test](../../skills/figma-e2e-test/SKILL.md)。`use_figma` 実行の低レベル作法は `figma-use`。
- **入口**: Figma作業はまず [mikeneko-figma](../../skills/mikeneko-figma/SKILL.md) を通る。共通規範（Spacer禁止/手描き偽装/アンチブリード/出典ゲート/OOUI原則/ページ編成原則/AA・14px）は **[mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md) §共通の禁止事項 が唯一の正典（SOT）**。本スキルは共通規範を《一行宣言＋ルールID（F-*）＋入口＋rulesの両方への→ポインタ》で参照し、**本スキル固有のゲート実行手順（§0表A/B/C/D・§3設計マッピング表・§4一括承認・§8(e)〜(h)逆監査の具体手順・proc:/abs:許可コード一覧・要素allowlist運用）だけを完全文で持つ**。

### 適用分岐（新規 / 既存改修 / 混在）を前方確定
- **新規作成のみ**: 本スキルで完結。
- **既存改修のみ**: [figma-ds-edit](../../skills/figma-ds-edit/SKILL.md) へ。
- **混在運用（新規＋既存改修）**:
  1. **マネージャー自身がスキル呼出主体**。本スキル§0で混在リスト（新規／改修を分離）を宣言。
  2. 本スキル§1〜§3を進める間、改修分は**並行で `Skill(figma-ds-edit)` 起動**して棚卸し・現物確認を実施。**ds-edit の棚卸し結果は本スキル§2の入力として引き継ぐ**（二重走査しない）。
  3. **§4ユーザー一括承認は新規分＋改修分のマッピング表をまとめて1メッセージで提示**。**ds-edit内で発生したエスカレ票（新規variant、新規variable、State B'等）も本スキルマネージャーが吸い上げて一括承認に束ねる**（ds-edit側で勝手に承認を取らない）。
  4. §5実装は新規分（本スキル）と改修分（ds-edit）を**領域別並列**で進める（同一ファイル同時書き込みは衝突回避のため避ける）。
  5. **プロトタイプ配線は design-create 専管**（§6として本スキルでのみ実施する）。**既存frameへのreaction張りは「改修」扱いとして§0改修対象リストに含める**（reactionは既存ノードへの変更なので改修スコープ監査の対象）。
  6. §7レビュー・§8自分の目は新規＋改修両方を対象。

## 鉄則（不可侵原則・最優先・全工程共通）
**第1ランク（不可侵・default-deny）**: 鉄則2 出典必須 ／ 鉄則4 生値禁止 ／ 鉄則13 OOUI=オブジェクトのビュー。番号は固定（他§のクロス参照を保つため付け替えない）。

1. **要件をまず理解する。** 着手前に「画面の役割／満たすべき条件／曖昧な分岐」を一文化し、**作成フレームリスト・改修対象リスト・遷移配線リスト**まで宣言する。リスト外は作らない。曖昧があれば実装前にユーザーへ確認するが、**質問は規模に応じて束ねる**（後述 S7「規模スケーリング」）。
2. **要件にない文言を加えない＝全テキスト出典必須・default-deny（F-SRC-1 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§出典系が正典）。** 各テキストに出典タグ（使い方は S7「文言・項目の取り扱い」。要素の存在は user/req/existing の3つだけ）を残す。`guess:` が3件以上を占めるならスコープ自体を要件主に確認。
3. **判断点は相談する。質問は束ねる。** 追加文言／新規変数／新規スタイル／新規コンポ／新規パターン等、自分で決められない分岐は実装前にユーザーへ4択 or 明確な質問で上げる。「よくあるやつ」「いい感じ」等の曖昧指示には9項目テンプレを丸投げせず、**最小コア版＋拡張候補リスト**の2点セットで確認（後述 S7「曖昧指示の扱い」）。
4. **生値を残さない（F-QLT-5、色はトークン: F-QLT-1 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§品質系）。** 直書きhex・font-size・line-height・font-family・letter-spacing・spacing・radius・elevation 禁止（バインド詳細は S7「変数・スタイル必須ルール」）。**例外**: DS不在ルートで primitive 変数を**初回定義する瞬間のみ**生値OK（設計マッピング表に `primitive-def:` タグで明示）。
5. **新規バリアブル/スタイル/コンポは無断で作らない。** 棚卸しで既存に類似が無いと**全Nページ走査済の上で**確定したうえ、命名・所在コレクション・スコープ・参照元込みでユーザーへエスカレーション。承認まで生値で進めず保留。**ファイルが空・DS未着手のときは「ファイル空・DS未定義」の一行で代替してよい**（儀礼スクショ不要）。
6. **既存DS流用は命名一致では決めない。** 候補が見つかったら、**既存使用箇所を最低1件取得して用途一致を検証**してから採用。State A（完全一致）／State B（部分一致・要承認）／**State B'（合成内部欠落・要承認）**／State C（不採用＝新規必要）の4分類（後述 S7「DS流用判定」）。
7. **発見ファースト・決め打ち禁止＝不在断定・重複作成禁止（F-PLC-3 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§配置系）。** トークン名・コンポーネント・ノードIDはファイルごとに違う。
8. **段階的に作る、一気にやらない。** 1画面を1回の `use_figma` で完成させない。論理ブロック単位（コンテナ→骨格→セクション中身→テキスト確定→**プロトタイプ配線**）で分割。各段でスクショ自己確認＋自分のゲート。
9. **use_figma の atomic 性を信じる、レスポンス検証は毎回。** 失敗時はスクリプト全体が未実行。エラー瞬間に停止し、現状を `get_screenshot` で確認、原因特定してから次へ。連投禁止。
10. **見た目が部品なら実体も部品・手描き偽装禁止（F-CMP-2 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§部品系）。** タブ／入力／バッジ／ボタン／チップ／メニュー行など DS に実体がある部品は必ず instance 化。判定はF-CMP-5のdefault-deny（→入口§部品系）: 分母は『部品に見えるもの』でなく**スタイル付き全ノード**。`raw:`例外は§4で承認・§8で反証。
- **2コピー則: 実装中に同一構造を2回目にコピーしようとした時点で手を止め、`new-comp:`票でコンポ化に寄り道する（別画面への複製・同一画面の状態フレーム間の複製・画面内繰り返しのいずれも対象。単位基準の正本=[figma-component-design](../../skills/figma-component-design/SKILL.md)§コンポーネント化の単位基準）。**
11. **検証はサンプルでなく全件被覆。** 配置した全要素＋全配線を見る・node type が `INSTANCE` か・mainComponent が想定通りか・detach されていないか・fill/typo がバインド済みか・**reactionが正しく張られているか**、を1件ずつ。
12. **報告は正直に。** 残課題・未承認の保留事項を隠さない。先回りの正当化や未検証の約束をしない。
13. **各フレームはオブジェクトのビューとして起こす（F-OOUI-1〜7 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§OOUI系が正典）。** frame=オブジェクト(名詞)のビュー(collection/single)を先に確定・動詞はモードレスなアクション・種別/区分/貸出期間/返却期限はプロパティ・状態・アクションに畳む。例外(逐次タスク)は `proc:` 理由コード宣言制（許可コード一覧は S7「手続き的フロー逃がし弁」＝本スキルが正典）。[feedback_wireframes_ooui_bound](../../docs/feedback_wireframes_ooui_bound.md)

## 標準オーダー（0→9）
工程番号はこの1系統のみが正本（ロールの丸数字は S5、対応はレジェンド参照）。

- **0. 要件確定〔委譲不可・自分〕** — S7「要件理解の手順」に沿い、**規模クラス・作成フレームリスト・改修対象リスト・遷移配線リスト・OOUIビューインベントリ（表A/表B）・オブジェクト関係と操作権限（表E/表F）・ページIA宣言（表C/表D）**まで含めて1枚にし、ユーザー一括confirm を取る。**ここが固まらない限り着手しない。**
- **1. 現物確認＋既存コピー横断走査＋視覚言語抽出（読み取り）** — 同じファイル内（or実アプリ）の**既存類似・姉妹画面**を `get_screenshot`＋`get_metadata` で観る。**双子の同定は工程1の必須出力（fail-closed）**: 着手前に作る画面のビュー種別（collection/single/proc）を要件だけから確定し、"同一ビュー種別"の既存画面だけを双子候補にする——一覧を詳細の双子に選ばない（by construction）、DSファイルのfileKeyはTWIN不適格。同種別ゼロならfail-closedで基準画面を1問。選定結果を `TWIN: <fileKey>/<node-id> view=<種別> 双子根拠1行` として宣言し、**空なら実装委譲に進めない**（正本→[mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§品質系 F-QLT-7）。**既存プロダクトの画面を作る/刷新するときは、この双子が視覚SOT**（F-QLT-7）: 色の使い所（アクセントだけか塗り面か）・カード様式・バッジ形状・余白リズム・アプリ枠の有無を言語化し、その語彙内で設計する。**DSファイルの部品/トークンは実装語彙であって見た目の基準にしない**（DS単独で起こすと実アプリと別物になる）。さらに**今回扱うラベル候補について全ページのテキスト走査**を行い、既存表記を確認（表記揺れを増やさない）。**ファイルが完全に空のときは「空でした」の1行宣言で完了**とし、儀礼スクショは不要。**さらにTWIN宣言と同時に参照ファースト＝REF宣言を出す（F-PRC-11 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§進め方系が正典）**: `lazyweb_search`（2〜6語の具体UIパターン名＋platform=プロダクトの確定事項から）で実参照UIを1〜3件取得し、各件を《①クエリ ②参照名 ③なぜ良いか根拠1〜3行=構造の言語（原画化の本体） ④流用候補要素の`[REF:参照名]`タグ》で固定。ヒット0件はクエリ2本以上の空振り記録＋ユーザー報告。**REF宣言なしで工程3設計に入らない**。TWIN=視覚SOT／REF=設計根拠の供給源で役割が別（REFを一貫性基準にしない）。
- **2. 棚卸し（読み取り）** — 既存コンポーネント／変数／テキストスタイルを全走査で積極列挙（姉妹スキル [figma-ds-edit](../../skills/figma-ds-edit/SKILL.md) の棚卸し runbook を流用）。**ファイル空時は「DS未定義」の1行で完了**。
- **3. 設計＋ゲート判定** — **UI/情報設計（どんな画面構造・レイアウト・視覚方針にするかの"決定"）は、consequential な画面ではFableサブエージェント（別エージェントチーム）に委譲する**（[mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§進め方系 F-PRC-7・CLAUDE.md設計委譲方針）。渡すのは**双子/姉妹画面の実スクショ画像を直接**（要約テキストでなく）＋要件＋DS棚卸し結果＋**工程1のREF宣言（参照名＋なぜ良いか根拠込み・F-PRC-11）**。視覚階層・IA・既存への馴染みはモデル地力が効く工程なのでSonnet格下げ禁止。**マネージャー(main)は"設計そのもの"は委譲するが、その成果を設計マッピング表へ落とし込む突合・ゲート判定・エスカレ切り出し（この工程）は委譲不可で担う**。画面構造／使うコンポーネントID＋バリアント／使う変数・テキストスタイル／**全テキストの文言と出典**／**遷移配線リスト**を**設計マッピング表**（フォーマットは S7、改修行・繰り返し要素も含める。frame行に object / view(collection|single|proc:<code>) / modeless-action 列を追記）にする。①新規文言、②新規変数/スタイル、③新規コンポ（component列が4値で埋まらない要素は自動的に`new-comp:`票として切り出す）、④既存と異なる扱い、⑤機能必須として追加した要素、**⑥ OOUI逸脱(動詞フレーム/種別選択画面/ウィザード化/独立区分・繰り返しフレーム)** の6種は**エスカレーション対象**として切り出す。
- **4. ユーザー一括承認** — 3 の設計＋エスカレーション項目を**1メッセージにまとめて**提示（L規模は領域別）。**改修分のマッピング表も同じ承認に含める**（混在運用時）。**ビューインベントリ（表A/B）・オブジェクト関係と操作権限（表E/F）・ページIAマニフェスト（表C/D）・`proc:`/`cross-object:` 例外フレーム＋各例外の反証可能な正当化1行も同じ承認に束ねる**。**auto-layout既定から外す `abs:<code>` 例外＋各々の『なぜgap/paddingでは表現できないか』理由1行も同じ承認に束ねる**（新たな承認往復を増やさない）。**要件外の`[REF:]`タグ付き要素（参照UIからの流用候補）も承認バッチに明示列挙し、未承認`[REF]`要素は実装禁止（F-PRC-11／F-SRC-2アンチブリード）**。承認前に書き込みしない。
- **5. 実装（書き込み・段階）** — `/figma-use` 遵守。1段＝1論理ブロック。各段で自己スクショ→レスポンス検証→OKなら次。同一ファイル同時書き込み禁止（**ただし重ならない領域は並列可**）。
- **6. プロトタイプ配線** — §0の遷移配線リストに従って、新規/既存問わず **Reaction (On click → Navigate to)** を設定する専用段。**遷移配線リストが空（1画面案件）の場合は「対象なし」で完了宣言してよい**。OOUI逆監査の1回目（§5実装後・配線前・構造項目のみ）は本段の前に実施済みであること。配線済み状態での完全判定＝2回目は§8(f)で実行（発火規定の正本→ S7「OOUI逆監査」）。
- **7. 独立レビュー（読み取り・全件）** — 実装者と別個体・敵対的。レイアウト・コピー・変数バインド・instance実体・**reaction整合・object/view整合・modeless退行（動詞フレーム化やウィザード化）**を全件で確認。
- **8. 自分の目で最終確認〔自分のゲート〕** — マネージャー直接実施。**(0) この工程の最後に F-CMP-7 の3run（run1複製範囲→run2親辿り→**run3 F-CMP-5スコープ**）を実走する。セッション最後のuse_figmaがrun3でないとStopフックが必ずBLOCKするので、他の確認作業を後ろに置かない**（手順の正本＝[mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§部品系 F-CMP-7）。**具体手順**: (a) 作成フレーム全数を `get_screenshot` で目視 (b) 主要instance を `get_metadata` で `INSTANCE` / mainComponent 一致 / detach無しを抽出確認 (c) 遷移配線リストN件と実装reaction件数のN突合 (d) 設計マッピング表の各行が実装と一致。**件数突合は cardinality 対応式**: 設計N≦実装N＝レビューN（template 行は設計1で許容、実装＝レビューは厳密一致）、配線N＝reactionN（こちらは厳密一致）。(e) **逆差分監査（実装→宣言）**: 実装の全要素/フィールドを列挙し§0/§3宣言と逆向き突合、未宣言（template繰り返し除く）はブリード/スコープ膨張として削除かエスカレ（手順の正本→ S7「要素・フィールドの出典とアンチブリード」）。**要素の合格語彙は `user:`／`req:`／`existing:` の3種のみ**（後の改定で`inherent:`・`guess:`・承認済み`[REF:]` は廃止）——参照UIから写した要素は、本人の回答の逐語で `user:` に引き直していない限り落とす（F-SRC-1／F-PRC-11／F-SRC-2）。(f) **OOUI逆監査（実装→宣言）**: 手順・発火規定（計2回）の正本→ S7「OOUI逆監査」。(g) **ページ編成逆監査**: 手順の正本→ S7「ページ編成逆監査」。(h) **auto-layout厳守逆監査（実装→宣言）**: 手順の正本→ S7「auto-layout厳守逆監査」。(i) **重複監査〔F-CMP-6〕＝(0)のrun1+run2そのもの（別実行ではない）**: ## 詳細・判断基準

### 規模スケーリング（**最初に判定して編成と往復回数を決める**）
要件確定の最初にマネージャーが**規模クラス**を判定し、編成と承認往復回数を宣言する。

| クラス | 条件 | 編成 | 承認往復 |
|---|---|---|---|
| **XS-DS整** | 1画面・要素20未満・DS整備済 | ①②⑥兼ね、④単一段 | 1往復 |
| **XS-DS無** | 1画面・要素20未満・**DS未定義**（ファイル空） | マネージャー単独＋④単一委譲 | **1往復・短縮ルート発動**（後述「最小要件 × DS不在ルート」） |
| **S** | 1-2画面・要素50未満 | 標準編成（並列①②⑥） | 1往復 |
| **M** | 3-5画面、または要素100未満 | 標準編成、④領域分割 | 1-2往復 |
| **L** | 6画面以上、要素100以上、**または「操作可能なデータを扱う」画面**（ユーザーがソート/フィルタ/選択/編集で能動的にデータ集合を操作する画面） | 標準編成、④領域別並列 | **領域別2-4往復**（フィルタ仕様／ソート仕様／状態網羅／権限差 等を個別領域で詰める） |
| **XL** | 0→1ファイル＋複数画面＋DSも含めて構築 | DS不在順序（後述）必須 | 領域別＋段階別承認 |

**L判定の注意**: 「一覧」「ダッシュボード」「管理」等の語彙だけでL自動昇格しない。**ユーザーが能動的にデータ集合を操作する**（ソート列を押す／フィルタを変える／行を選択して一括処理する／編集する）画面のみL。静的なリスト表示やウィジェット並べは S/M で扱う。

**往復ルールの統一**: 「束ねる」と「分ける」の二段運用は規模クラス表が決定的。**領域内では束ねるが領域間では分ける**。XS〜Sは束ね1往復、Mは束ね1-2、Lは領域別2-4、XLは段階別。1往復厳守と領域別2-4は矛盾せず、規模クラスで分かれる。

### 要件理解の手順（0 の中身）
着手前に以下を**1枚に書き出してユーザーに見せる**。**質問は規模クラスに応じて束ね**、未指定項目は最初のQ&Aに必ず含める。

#### 必須項目（全規模共通）
- **画面の役割（1行）**: この画面で何が達成されるか。
- **画面サイズ・プラットフォーム・モード**: mobile（幅px）／web／responsive、light/dark対応の有無。
- **オブジェクトモデル＋OOUIビューインベントリ（表A/表B）**: 書く順は**表A（オブジェクト）→表E/表F（関係・操作権限）→表B（ビュー）**で、ビューは先に整えたオブジェクト・関係・操作権限から導く。作成フレームリストは**先にビューを確定してから導出する**。動詞・手続き・種別は表Aに畳み、独立objectにしない（後述「OOUIビューインベントリ」）。
- **ページIA宣言（表C frame帰属／表D Page構成）**: フレームをどのPageに配置するかを**オブジェクト単位**で宣言（後述「ページIA宣言」「ページ編成ガイド」）。新規Pageは新しいオブジェクトが登場するときだけ。
- **作成フレームリスト（新規）**: 今回新しく作る画面/フレームを全列挙（表Bから導出）。**状態バリエの有無**を§0段で宣言（「通常状態のみ」／「状態複数あり：詳細は§4で承認」）。複数ありなら§3マッピング表で全状態フレームを列挙し、§4で一括承認。
- **改修対象リスト（既存）**: 既存画面に追加・修正を入れるフレームを全列挙。改修分は [figma-ds-edit](../../skills/figma-ds-edit/SKILL.md) に委譲。
- **派生・補助画面の見込み**: 入力→確認→完了 等の派生画面を仮置きし、要件時にユーザーに「この派生は要るか」を4択で問う。
- **遷移配線リスト**: from(画面/要素) → to(画面) のペアを全列挙。**戻る・キャンセル動線**も必ず明記。**1画面案件で配線が無い場合は「配線対象なし」と明示**。**画面間遷移は§0で全列挙、画面内状態間遷移（フィルタ結果0件→クリア→通常等）は§3マッピング表確定時に追加**（§0の段階で全状態×全遷移の積を埋めようとしない）。

- **使うべき既存パターン**: 既に存在する同種画面の参照（あれば node-id）。
- **曖昧分岐**: 自分で決められないところを箇条書きで列挙→ユーザーへ。

- 表A オブジェクト棚卸し（動詞・手続き・種別はここに書く＝独立objectにしない）:

### 文言・項目の取り扱い（最重要・鉄則2）

#### 出典タグ（定義の正典は入口 F-SRC-1。後の改定で「項目は本人が決める、勝手に作るのはやめる」を明文化）
**要素が在ってよい出典は `user:`（本人の逐語）/ `req:`（議事録・要件文書の逐語＋行）/ `existing:<nodeId>`（既存画面・default-keep）の3つだけ。** `ds:` / `placeholder:` / `primitive-def:` は在ることが決まった要素の見た目・値の根拠。`inherent:` / `guess:` / `similar:` / brief / REF・参考サービスは出典にならない（実装ワーカーに渡す設計書にこの語が1行でもあると `item-provenance-pretool.sh` が止める）。本スキルでの使い方:
- `req:` は要件文中の動詞流用可（要件「ログインできる」→ ボタン「ログイン」）。`ds:` はコンポ既定テキストをそのまま採用するとき。`existing:` は表記揺れ吸収のため既存の同役割表記を流用するとき。
- `placeholder:` はサンプル氏名・金額・備品名等の表示用ダミーデータと、user/req/existing に語が無い文言の仮置き（質問に積み、最終報告で明示）。
- `guess:` / `similar:<参考機能>` は**拡張候補リスト（＝本人への質問）の中だけ**で使う。本人の回答が出たら `user:` に引き直す。実装マッピング表・実装ワーカーに渡す設計書には書かない。
- `primitive-def:` は DS不在ルートで primitive 変数を初回定義する瞬間の生値タグ（鉄則4の唯一の例外。設計マッピング表に明示、後述「DS不在ファイル」）。

#### 機能要素の確認リスト（置く根拠ではない）
**このリストは要素を置く根拠にならない（後の改定で明文化）。** 下の要素も、user/req/existing で名指しされたときだけ置く。名指しが無ければ置かずに AskUserQuestion の質問に積む（例: 一覧にソート・フィルタ・タブを「データ操作系だから普通ある」で足さない）。リストは質問の抜け漏れ防止に使う。

##### 共通（フォーム・詳細・コンテンツ系）
- 入力フォームの送信ボタン・キャンセル/戻る。**ボタンラベルは (a) 要件文中の動詞を流用（"ログインできる" → "ログイン"）／ (b) 既存画面の同役割表記を流用**。発明禁止。
- 値変更系の「送信中／成功／失敗」状態の表示位置（**メッセージ文言**はエスカレ対象）
- バリデーションエラーの表示領域（メッセージ文言はエスカレ対象）
- ヘッダタイトル・戻る矢印
- 入力欄ラベル（最小限の機能語：要件「メール」→ 「メールアドレス」可、揺れ吸収はユーザー確認）
- input type に伴う技術的属性（password/email 等）

##### データ操作系（一覧・テーブル・管理画面）
- **ソート**: 列ヘッダの▲▼アイコン、ソート状態の視覚表現
- **フィルタ**: 絞り込みトリガ、フィルタpill、適用、リセット、クリア、条件追加
- **ページネーション**: 前へ/次へ、件数表示、ページサイズ選択
- **選択**: 全選択チェックボックス、N件選択中バー、選択解除
- **エラー状態**: 再試行ボタン、エラーメッセージ表示領域（文言はエスカレ）
- **空状態**: empty data vs empty filter の使い分け表示領域（文言はエスカレ）
- **ローディング**: スケルトン / スピナーの配置位置

**ホワイトリスト外**（確認用再入力、現在値表示、ヘルプ文、注意書き、補足説明、空状態メッセージ文言、業務フロー固有の項目）は引き続きエスカレーション対象。**迷ったらエスカレ側に倒す**。

#### 表示vs文言の境界
- 「表示位置を置く」と「**そこに置くテキスト**」を分離。位置・領域の確保も user/req/existing で名指しされた要素だけ。メッセージ文言は別途エスカレ。
- 確保したフレーム/領域は§0「作成フレームリスト」の状態バリエ宣言と一致させる（暗黙に新規フレーム/状態が生えるのを防ぐ）。

#### UIの機能語と `placeholder:`
- UIの機能語（ラベル「メールアドレス」、ボタン「ログイン」等）は `req:`（要件の語の流用）か `existing:`（既存画面の同役割表記）で取る。どちらにも無ければ `placeholder:` で仮置きして質問に積む。
- `placeholder:` の仮置き文言は最終報告で「未確定の文言」として全件列挙する。
- 「現在のメールアドレス: xxx@yyy.com」のような**表示**は、(a) その表示要素を出すか自体がエスカレ対象、(b) 出すと決まった後の値は `placeholder:`、(c) ラベル「現在のメールアドレス」は `req:`/`existing:` か、無ければエスカレ。

#### プロジェクト辞書化
データ操作系画面で初めて作るとき、ホワイトリスト外の機能語（「絞り込み」vs「フィルタ」、「適用」vs「決定」等）の**確定表記をプロジェクト辞書として記録**（DSページにテキストフレーム or コメントで）。次以降の画面はこれを参照し、毎回確認を繰り返さない。

### 要素・フィールドの出典とアンチブリード（鉄則2の「要素版」・最重要）

鉄則2（文言）と同じ規律を**要素・フィールドそのもの**（「これが画面に存在するか否か」）にも適用する。原則の正典は [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§出典系。一行宣言:
- **全要素は出典必須・default-deny（F-SRC-1）**: 各要素は `user:` / `req:` / `existing:<nodeId>` のどれかに辿れること。辿れない要素は置かず、AskUserQuestion で1問聞く。
- **他案件の記憶は出典にならない（F-SRC-2 アンチブリード）**。〔反面教師の実例1行（架空の例）: レシピ共有アプリの「フォロー中の作者だけに表示する」を無関係な会員登録画面に足す類 → [feedback_element_provenance_antibleed](../../docs/feedback_element_provenance_antibleed.md)〕
- **「良かれ」は行動でなく提案へ（F-SRC-3）**。
- **ユーザー明言・ユーザーが見せた現物は最上位の出典（F-SRC-4）**: レビュアーの「参照1フレームに無い＝発明」で明言スコープを削らない。

本スキルでの運用（allowlist・固有手順＝ここが正典）:
- **別サービス（参考サービス・REF・lazyweb の参照を含む）の同種画面からフィールド・タブ・編集操作を写すのは `guess:` 扱い**（=本実装不可）。「良かれ」要素は §0/§4 の「拡張候補リスト（`guess:`）」に積んで本人に聞き、回答の逐語を `user:` として引き直してから置く。
- **§3マッピング表に要素行の出典タグを必須化。** 各要素行に上記タグを書く。タグの無い行は設計を通さない。
- **§8で逆差分監査（実装→宣言）。** §8の件数突合に加え、**実装に存在する全要素を列挙し、各々が§0作成リスト/§3マッピング表に宣言済みか**を逆向きに突合する。宣言に無い要素が実装に出ていたら**ブリード/スコープ膨張として削除、必要ならエスカレーション**。（従来の「設計N≦実装N」は template 繰り返しのみ許容。それ以外の未宣言要素は不可。）

### 手続き的フロー逃がし弁（proc:理由コード・default-deny・根拠宣言必須・閉じた列挙）
collection/single で書けない frame は閉じた理由コードを1つ付ける（§3エスカレ⑥／§4承認対象）:

- `proc:auth` — 認証/資格情報handshake(閲覧可能なドメインobjectが無い)
- `proc:txn-commit` — 取引の原子性＋ドメイン必須の順序(決済・不可逆submit。順序がUI都合でなくドメイン制約)
- `proc:dependent-branch` — 後続フィールド集合が前の回答で本質的に分岐(フラット提示だと無効な組合せを問う)。単なる値選択(即時/予約・ロール・種別)は分岐でなくプロパティ→不可
- `proc:legal-consent` — 外部規定の強制熟慮(同意/KYC/破壊的確認)
- `proc:onboarding` — 初回限定の教育的逐次(スキップ可・定常手段でない。同じ事をモードレスに行えるobjectビュー経路が別に存在することが条件)
- `proc:utility` — 非object面(404/error/splash/印刷ダイアログ)
- `cross-object:` — 複数objectを束ねるホーム/ダッシュボード/サマリ(各objectのcollection/singleへ確実に降りられること)

旧表記 `non-object:` は廃止＝非object面(404/error/splash等)は `proc:utility` を使う（閉じた列挙の外に並列タグを増やさない）。列挙外は `proc:other` のみ可、自動承認されず必ずユーザーへエスカレ(enum拡張は人間統制下)。各 `proc:` に1行の反証可能な正当化必須（「なぜobjectのcollection/single＋モードレスchipにできないか」を具体的ドメイン制約=順序強制/原子性/法定熟慮/真の分岐 で）。**無効理由(=書いたら差し戻し)**: 「綺麗」「ユーザーが期待」「作成フローだから」。例外スコープはcommit/handshakeの最小逐次スパンのみ。それが包むobject(Cart/Order/Account)の閲覧・編集ビューまで例外にしない。§8(f)で `proc:` 全件のリフレーム反証（レビュアーが能動的にOOUI化を試み、候補object名指し＋失敗するドメイン制約を文書化。書けなければproc:却下→OOUI化）を回す。

### auto-layout厳守の逃がし弁（abs:理由コード・default-deny・根拠宣言必須・閉じた列挙）
auto-layout/gap/paddingで組めない（=非auto-layout・絶対配置・隙間専用空ノードが正当な）要素は閉じた理由コードを1つ付ける（§0表Bの出典列 or §3マッピング表に明示／§4承認対象／§8(h)で全件反証）。出典タグ・proc:理由コードと完全同型:

- `abs:overlay-decor` — overlayバッジ/フォーカスリング/通知ドット等、**親のauto-layout計算に影響を与えてはいけない装飾**(layoutPositioning=ABSOLUTE。figma-component-design §オートレイアウト設計＞『絶対配置を使ってよい唯一のケース』と整合)。
- `abs:fixed-overlay` — モーダル/トースト/FAB/ドロワー等、画面フローから外して固定オーバーレイする最上位レイヤ。
- `abs:divider` — 意図的な区切り線(ただしfill/strokeのpaintを持つ実体=Spacerでない。隙間でなく『線』であることが条件。場当たり線で取り繕うのは別途禁止)。
- `abs:empty-state-slot` — 空状態/プレースホルダの予約枠(instance実体or名前付きslotで、将来コンテンツが入る宣言付き。無記名の純空ノードは不可)。
- `abs:test-canvas` — DSページ/別Pageに隔離した全property組合せ等の検証用テスト並べ(成果物Pageには置かない。隔離規律と整合)。

列挙外は `abs:other` のみ可、自動承認されず必ずユーザーへエスカレ(enum拡張は人間統制下)。逃がし弁は『なぜgap/padding/Boolean Visibilityで表現できないか』を装飾性・最上位レイヤ性・線の意味・空状態の予約という具体根拠で書けたときのみ通る。**無効理由(=書いたら差し戻し)**: 「綺麗」「位置合わせが楽」「なんとなく」「AL組むのが面倒」「普通こうする」「見た目が同じだから」。§8(h)で全 `abs:` のリフレーム反証（レビュアーが能動的にgap/padding化を試み、失敗する構造制約を文書化。書けなければabs:却下→auto-layout化）を回す。

### `raw:`例外コード（閉じた列挙・これ以外は不可）
スタイル付き非INSTANCEノード（F-CMP-5 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§部品系が正典）を例外として置くときの理由コード（§3マッピング表component列に明示／§4承認対象／§8で反証）。宣言した例外ノードはノード名を`raw:<コード>`にする（audit-structure.jsは名前prefixで機械照合。台帳件数とのN=N突合が§8の合格条件）。abs:例外も同様にノード名`abs:<コード>`。出典タグ・proc:/abs:理由コードと完全同型:

- `raw:one-off-decor` — この画面限定の装飾で再利用ゼロが根拠として書けるもののみ
- `raw:shell-region` — 画面リージョンの殻（サイドバー殻・ヘッダーバー等のレイアウト枠）。**fillは変数バインド必須**（raw値なら不合格=F-QLT-5）
- `raw:pending-comp` — コンポ化票承認待ちの暫定。票IDの併記必須、承認後に埋め戻す
- `raw:other` — 自動承認なし。必ずエスカレーション票で人間の判断を仰ぐ

### DS流用判定（State A/B/B'/C）
- **State A（完全一致採用）**: 既存使用箇所の用途・データ種・並びが新規用途と一致。そのまま採用。
- **State B（部分流用・要承認）**: 命名は近いが用途差あり。**「採用案 + 差分」をエスカレ票に切り出し**承認を得る。
- **State B'（合成内部欠落・要承認）**: 合成コンポ（Table/Form/Modal等）の本体は State A だが、内部の特定パターン（ソート可ヘッダ、行選択、フィルタpill等）が既存に無い。**欠落部品リストを1つのエスカレ票に束ねて**承認を取る。**束ねる上限は5項目まで**（超えるなら本体採用自体が不適切でState Cへ降格、または合成パターンの再設計をユーザーへ）。
  - **発見契機**: §2棚卸し時に「**合成コンポの内部探索**」を必須化（mainComponent内のバリアント軸とスロット候補を1段ドリルダウンして欠落を検出）。§5実装中に発覚した場合は**即§4へ巻き戻し**、束ね承認を取り直す。実装段で勝手にState Aで埋めず保留する。
- **State C（不採用）**: 命名一致でも用途違い・データ型違い。新規が必要なら鉄則5へ。

### 変数・スタイル必須ルール（鉄則4）

#### 色
- primitive/パレットを直接当てない。**役割名のセマンティック変数**を当てる。
- 役割: 主文字／補助文字／リンク・強調／枠・区切り／面（背景/カード/入力）／ブランド主色＋上の文字／状態色（成功/警告/エラー/情報）。
- モード（light/dark）対応。fill は必ず変数バインド。

#### タイポ
- **名前付きテキストスタイル優先**。役割／サイズに合えば適用。
- スタイルが無くタイポ変数の文化なら**変数バインド**。font-size と line-height は同じスケール段から必ずペアで。
- 任意px禁止。必要な段が無ければ「不足」を報告。

#### 間隔・角丸・影
- gap/padding/border-radius/elevation も生値禁止。space/radius/effect 変数があれば必ずバインド。

#### コンポーネント絡み
- インスタンス内部の色/サイズは**生値で上書きしない**。バリアント／プロパティで変える。
- 実データが入る入力欄は Filled 系バリアントを使う。

### 新規バリアブル/スタイル/コンポ作成時のエスカレーション（鉄則5）

エスカレーション票:
- **不在の証拠**: 全Nページ走査済み／検索した変数名・スタイル名・コンポ名／棚卸し結果のスクショ。**ファイル空・DS未着手のときは「ファイル空・DS未定義」の一行で代替してよい**。
- **流用案（あれば併記）**: 既存の近いトークン／スタイル／コンポを「これで代替できるか？」と並記。
- **新規提案**: 命名／カテゴリ・所在コレクション／モード（light/dark）／スコープ／初期値／参照元の使用箇所。
- **影響範囲**: 既存への波及（共有資産か、ローカルか）。
- **可逆性**: 後で消せるか／改名コスト。

承認後にだけ作成。**未承認の時は当該箇所を未完成として報告**（暫定生値で「とりあえず置いた」をしない）。

### DS不在ファイル（0→1）の作業順序
DSが整っていない/まだ無いファイルで新規デザインを起こす場合、**順序を飛ばさない**。各段でユーザー承認を取るが、**最小要件時は1往復一括承認に短縮**。

1. **primitive 変数**: color パレット／spacing／radius／typography スケール／effect。**生値はここで一度だけ定義**（鉄則4の生値禁止の唯一の例外。設計マッピング表に `primitive-def:` タグで明示）。
2. **semantic 変数 / テキストスタイル**: 役割名を primitive のエイリアスとして定義。
3. **トークンエイリアス**: state-success, link-default 等の追加層。
4. **atom/molecule コンポーネント**: Button / Input / Tag / Card / Avatar 等。
5. **画面組み立て**: 上記4までを使って画面を組む。

#### 最小要件 × DS不在ルート（XS規模の短縮ルート）
**判定条件**: ① 作成フレームが1画面 ② 要件記述が3文以下 or 入力項目3個以下 ③ 棚卸しで「DS未定義」確定。

このときに限り:
0. **§1現物確認・§2棚卸しは「空でした／DS未定義」の1行宣言で完了**（儀礼スクショ不要）。
1. **要件補完を1往復にまとめる**: 画面サイズ／プラットフォーム／submit後の遷移／エラー時の文言扱い／ブランド色の有無／**このファイルにDSや既存画面が無いがゼロから作ってよいか（別ライブラリ参照の有無）**を1往復のQ&Aで一括確認。
2. **DS最小セットを束ねて1回で承認**: ユーザーに対して**「ゼロ案＋拡張提案」の2列**で提示し、yes/no/採用範囲を選ばせる。プリセットを押し付けない（鉄則2・`feedback_element_provenance_antibleed` 準拠）。
   - **ゼロ案**: 「今回の要件に直接必要な分のみ」（例: ログイン画面なら neutral 黒/白/中グレー1段／space 4の倍数3段／typo 2段／radius 1段）
   - **拡張候補**: 「将来再利用するなら」neutral 5段までの拡張／brand色／danger等の追加 — **各候補に理由を付け**、ユーザーが ◯×で個別選択できる形に。
   - **暗黙のセマンティック多重化（surface/border/danger 等）は提案に含めるが、ゼロ案の時点では必須にしない**。ユーザーが要らないと言えば作らない。
3. **atom 最小セット（Button / TextField）のみ事前承認**で作成、それ以外は画面段で発覚した時のみ追加。
4. **段階実装は領域単位ではなく画面単位で1回**でよい。

**短縮ルートでの語確定優先順位**: プロジェクト辞書がまだ無い状態でラベル/ボタン文言を確定するとき、(1) 要件本文の動詞流用（`req:`）→ (2) 既存画面の同役割表記（`existing:`）→ (3) どちらにも無ければ `placeholder:` で仮置きして要件補完Q&Aへ追加、の順で決める。**1往復のQ&Aを破ってまで個別の語をエスカレしない**（仮置きのまま進めて最終報告で未確定の文言として明示）。語を決められないことを理由に要素そのものを足してはいけない。

短縮ルートを使ったことは、最終報告で必ず明示する。

### 設計マッピング表のフォーマット（③で必須）

要素マッピング表（frame行に object / view / modeless-action 列を追記）:
```
| frame | object | view | section | element | cardinality | scope | component(id/variant) | text | modeless-action | 出典 | binding(color/typo) |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 備品詳細 | 備品 | single | ヘッダ | 戻る | single | 新規 | IconButton/back | — | — | ds:123:456 | color/icon-default |
| 備品詳細 | 備品 | single | 主情報 | 備品名 | single | 新規 | text | サンプル備品名 | 編集chip | placeholder | typo/heading-m |
| 予約一覧 | 予約 | collection | 本体 | 予約行 | template(N=8) | 新規 | TableRow | (テンプレ1行) | 行選択/詳細へ | placeholder | (内蔵) |
| 設定 | 設定 | single | メニュー | 通知設定行 | single | 改修 | MenuRow | 通知設定 | — | req | (内蔵) |
```

- `object` / `view(collection|single|proc:<code>)` / `modeless-action`: frame=オブジェクトのビューであることを表現（鉄則13・OOUIビューインベントリ表Bと整合）。`collection/single` に収まらない frame は `proc:<code>` / `cross-object:` を入れエスカレ⑥（→「手続き的フロー逃がし弁」。非object面は `proc:utility`）。
- `cardinality`: `single` / `template(N=8)` / `dynamic` のいずれか。
- `scope`: `新規` / `改修` のいずれか。改修行は混在運用時に[figma-ds-edit](../../skills/figma-ds-edit/SKILL.md)へ委譲する対象（reaction張りも改修扱い）。
- 実装マッピング表で要素の存在の出典として許容されるのは `user:` / `req:` / `existing:` の **3種**だけ（後の改定で確定）。`ds:` / `placeholder:` / `primitive-def:` は見た目・値の列に書く。存在の出典が3種で埋まらない行はエスカレ対象。`inherent:` / `guess:` / `similar:` / brief / REF は実装マッピング表に書かない（`item-provenance-pretool.sh` が止める）。
- **component列の値域は4値のみ**: `ds:<componentId>/variant`／`new-comp:<コンポ化票ID>`（[figma-component-design](../../skills/figma-component-design/SKILL.md)へ委託し、票の承認・部品完成後にIDを埋め戻してから当該要素の実装に入る）／`raw:<コード>`（閉じた列挙のみ・根拠1行必須、→「`raw:`例外コード」）／`text`（テキストスタイル適用済みの生TEXT。F-CMP-5対象外・F-QLT系ゲートで検証）。**空欄・自由記述の行は設計ゲートを通さない**（出典タグと同じdefault-deny）。

#### N突合の定義（cardinality対応）
- **マッピング表のN（設計N）**: `single` は1、`template(N=K)` は1（テンプレ1行）、`dynamic` は1（型のみ記載）。**設計承認はテンプレ1行で完了**。
- **実装後の要素件数（実装N）**: `single` は1、`template(N=K)` は K、`dynamic` は実体ベース。
- **レビュー件数（レビューN）**: `single` は1全件、`template(N=K)` は**テンプレ構造正しさ＋K個全体の placeholder 多様性チェック**（テンプレ通りでない異常がないかを全件目視。同じテンプレ文字列でOK）、`dynamic` は K 個サンプリングではなく実体ベース全件。
- **件数突合**: 設計N≦実装N＝レビューN。「設計1：実装K」は許容、「実装K：レビューM(<K)」は禁止。

| 通知設定:戻る | On click | Navigate | 設定 | back |

### 状態バリエの分類別ホワイトリスト
§0「作成フレームリスト」で「状態複数あり」を選んだとき、§3で全状態を列挙する際の**最低網羅参照**。**種別/繰り返し/区分はframe追加でなく、同一(object,view)行の状態/プロパティとして扱う**（種別選択や即時/予約の分岐をframe化しない＝鉄則13）。

#### フォーム画面
通常／空／検証エラー／送信中／完了／不可

#### データ表示画面（一覧・テーブル・ダッシュボード）
通常／**完全な空（データ0件）**／**フィルタ結果0件**／**検索結果0件**／**初回ロード**／**部分ロード**／**取得エラー（再試行可）**／**権限不足**／**選択中**

#### 詳細画面
通常／読込／取得エラー／削除済／**競合（他者編集中）**／**ロール別表示差**

§0段ではこれら全部を列挙せず**「状態複数あり」の有無**だけを宣言。複数ありなら§3で全状態フレームを列挙し、§4で一括承認。§0で全状態を埋めようとして質問数を膨らませない。状態フレームはコンポーネントのプロパティ差し替えで構成し、フレームコピーで作らない（2コピー則: 状態フレーム間の複製もコピー1回と数える。正本=[figma-component-design](../../skills/figma-component-design/SKILL.md)§コンポーネント化の単位基準）。

### ページ編成ガイド（オブジェクト単位＝既定ページ単位）

■ 原則（一行宣言）: **既定は1オブジェクト=1Page・ストーリー(業務フロー)でPageを切らない・判断軸は必ず『どのオブジェクトのPageか』（F-PLC-4 → [mikeneko-figma-rules](../../skills/mikeneko-figma-rules/SKILL.md)§配置系＞既定のページ単位＝オブジェクト が正典）**。フローはプロトタイプ配線(必要なら俯瞰1枚)で表す。〔反面教師の実例1行: フロー単位Pageで同一オブジェクトのビューが複数Pageに散在＝フロー退行の物理固定化 → [reference_figma_ooui_page_gates](../../docs/reference_figma_ooui_page_gates.md)〕以下は本スキル固有の決定ルールと体裁（ここが正典）。

■ 迷わない決定ルール:
- **STEP0 オブジェクト同定**: 作る画面群が扱うメインオブジェクトを列挙(例 備品/予約/貸出履歴)。各frameを『どのオブジェクトの・どのビュー(collection|single|サブビュー)・どの状態』に必ず分類。分類できないframeは作らない(OOUI出典ゲートと同型のdefault-deny)。
- **STEP1 既定割当**: 1オブジェクト=1Page。collection＋single＋全状態＋そのオブジェクト固有のモーダル/インライン操作結果を同一Pageに並べる。
- **STEP2 散在判定**: あるオブジェクトのビューが2つ以上のPageに跨ったら違反(=1画面1ページのスメル)。1frameだけのPageを作らない。
- **STEP3 ストーリー**: 複数オブジェクトをまたぐ業務フローはPageを切る理由にしない→配線で表現、俯瞰は横断1枚『フロー俯瞰』に縮小サムネ/矢印で。フローごとにPageを増やさない。
- **STEP4 分割閾値(同一オブジェクト内のみ)**: 1Pageが破綻するときだけ分割可(目安: そのオブジェクトのframe数が概ね24枚超、または一覧と詳細で関心が完全分離)。分割時もプレフィックス共有＋隣接配置。区分/種別/貸出期間/返却期限は新オブジェクト扱いせずプロパティ・状態・アクションとして同一Pageに収める。
- **STEP5 優先順位**: オブジェクト軸＞ストーリー軸。複数オブジェクト合成画面(ダッシュボード等)は主オブジェクトで帰属、主が無ければ『横断/Overview』Pageへ(`cross-object:`)。
- **STEP6 既存ルール整合**: node-id指定はin-place、『別ページ』は新規Page、該当無し/複数候補で割れるなら着手前にユーザー確認。

■ わかりやすい体裁(まとめ):
- **Page命名**: 番号prefix＋オブジェクト名で固定(例 `00 Cover/IA索引`, `10 備品`, `20 予約`, `30 貸出履歴`, `90 Overview/ホーム`, `99 Archive`)。10刻みで挿入余地。Pageの並び自体がオブジェクトモデルの並びになる。分割は全角スラッシュで従属明示(`備品／一覧`)。
- **1Page内のframe並び**: 左→右に view種別(コレクション→シングル→サブビュー/モーダル)、上→下に状態(default→empty→loading→error→権限/区分差)。左右関係＝OOUIのcollection⇄single往復をキャンバス上でも表現。
- **セクション区切り**: Figmaの Section 機能(Group/外付けTEXT見出しの偽装は不可)で『コレクション』『シングル』『状態バリエ』『アクション派生』に分け、どのオブジェクトPageも同じSection骨格を使う。
- **frame命名**: `{オブジェクト}/{ビュー種別}/{状態}`(例 `備品/コレクション/default`, `予約/シングル/編集中`)で機械突合可能にし、view inventory各行と1:1一致。命名を見れば散在が即検出できる。
- 各Page左上に小さなIAヘッダ(担当オブジェクト名/内包ビュー一覧/外向き遷移)を置きPageを自己文書化。
- **隔離**: DS/共有コンポ本体はDSページ、全property組合せ等の検証用テスト並べframeは別Page/別領域へ隔離し成果物Pageに混在させない。
- **散在(違反)と横断(正常)の機械的区別**: 同一オブジェクトのビューが割れている=散在/違反、別オブジェクトのビューへ繋がっている=横断/正常。

### 段階的作成（暴走防止）
- 1画面を1回の `use_figma` で完成させない。論理ブロック単位（コンテナ／ヘッダ／フォーム1ブロック／ボタン領域／配線）で分割。
- 各段の終わりに**自分でスクショ確認**→OKなら次。
- `use_figma` 各呼出後にレスポンス検証（エラー無し、返却ID整合）。失敗時は**即停止 → 現状 `get_screenshot` → 原因特定 → 修正案提示**。連投禁止。
- 同一ファイル同時書き込み禁止。並列実装するなら重ならない領域に分ける。

### プロトタイプ配線（§6）
新規/改修問わず、画面間遷移は**必ず Reaction (On click → Navigate to → 対象フレーム)** で配線する。FRAMEの命名や見た目だけで「繋がっているつもり」にしない。

- **専用の一段**として切る。骨格・テキスト確定後に reaction だけ流す。
- **配線対象は §0「遷移配線リスト」と1:1突合**。リスト外の遷移を勝手に張らない。
- **戻る・キャンセル**の reaction も必ず張る。各遷移行は **trigger と back導線をペアで宣言**（例: 「設定→通知設定」と「通知設定→設定（戻る）」をペアで列挙、片方だけのリストは§0で差し戻し）。
- 共通コンポ（MenuRow等のインスタンス）の reaction は**インスタンス上で個別配線**するのが基本（main側に張ると全画面波及する事故）。
- **配線件数のN突合**: 遷移配線リスト件数 = 実配線件数 = レビュー件数（戻る/キャンセルも1件として数える）。
- **状態保持遷移**（一覧→詳細→戻る時にフィルタ・ソート・ページ位置を保持したい）の場合: (a) フィルタ済み状態の一覧フレームを別途用意して双方向reactionを張る、または (b) `Navigate(preserve:filter,sort,scroll)` を遷移配線リストに記載し実装側に注記、のいずれか。**「戻る=初期一覧」にしてはいけない**ケースは要件確定で必ず確認。
- **1画面案件で遷移配線リストが空のとき**は本段を「対象なし」で完了宣言してよい。
- OOUI逆監査の1回目（構造項目のみ）は配線前＝§5実装後に実施済みであること。配線済み状態での完全判定＝2回目は§8(f)で実行する（発火規定・裏取り対象の正本→ S7「OOUI逆監査」冒頭）。

### 全件レビュー（工程7・8）
- 配置した全要素＋全配線を**列挙→全部**を検証対象に（代表サンプル禁止）。広ければレビューをファンアウトし合計で全件カバー。
- 各要素で以下を1件ずつ判定:
  - 見た目がスクショで意図どおり。
  - **instance 実体監査**: node type が `INSTANCE`、mainComponent が想定通り、detach されていない。**`~/.claude/skills/mikeneko-figma/scripts/audit-structure.js`（use_figmaで実行）は偽装疑い（非INSTANCEが部品名を名乗る）の機械検出まで。mainComponent一致・detach無しの照合は手動 get_metadata で必須**（スクリプトでは検査できない）。＋F-CMP-5検出（スタイル付き非INSTANCE・instance率分数・fail-closed）も機械検出対象（未実測・初回試走必須）。mainComponent一致・detach無しは引き続き手動get_metadata必須。
  - **バインド監査**: fill/stroke が変数バインド、テキストがテキストスタイル or タイポ変数バインド。生値の残骸が無い（DS不在時の `primitive-def:` 除く）。
  - **文言監査**: 各テキストが `user:` / `req:` / `existing:` / `ds:` / `placeholder:` のいずれかに辿れ、`inherent:` / `guess:` や発明文が紛れていない。`placeholder:` の文言は最終報告に全件列挙。
  - **プロトタイプ配線監査**: §0「遷移配線リスト」と実配線が1:1で一致。trigger / action / destination を全件確認。戻る・キャンセルも含む。インスタンス上に張られているか（main側への誤配線がない）。
  - **改修対象のスコープ監査**: §0「改修対象リスト」外の既存frameに変更が入っていない。MenuRow等の追加行が detach されておらず instance のまま、項目順が壊れていない。
  - **OOUI/モードレス監査**: 各frameが「どのオブジェクトのどのビュー(collection/single)」として成立しているか・別オブジェクトの混入や動詞frame化(ウィザード化/step indicator/「次へ/戻る」主動線)でないか。
- **カバレッジ明示**: 「対象◯件／確認◯件」「配線◯件／確認◯件」。間引きは禁止。

### OOUI逆監査（§8(f) 詳細・実装→宣言）
**発火規定（正本・ここが唯一の記述、他§は本節への参照のみ）**: 計2回実行する。**1回目=§5実装後・§6配線前**（reactionが未配線なので構造項目のみ判定。collection⇄single の往復到達と線形ウィザードエッジの不在など配線依存の判定は保留）、**2回目=§8(f)**（(e)逆差分監査の直後・配線済み状態で reactionグラフ部を含む全項目の完全判定）。判定者は実装者と別個体（＝§7敵対レビュー）。

1. `get_metadata` で実装済み全top-level frameを列挙。
2. 各frameを機械判定:
   - (i) 表Bに対応行があるか。無い=未宣言フレーム→ブリード/退行として削除orエスカレ。
   - (ii) view種別を構造で裏取り(tag自己申告で合格にしない): collection=同型反復(リスト/テーブル/カードグリッド)が画面の主役 / single=単一オブジェクト1件の属性・状態提示。
   - (iii) modeless退行シグナル検査(1つでも該当=§4へ巻き戻し): frame名/ヘッダが動詞+ステップ名(「○○を作成」「ステップ1/3」「方法を選ぶ」)、step indicator/進捗ステッパー(生rect+TEXTの偽装ステッパーも疑い構造で見る)、frame下部の「次へ＋戻る」ボタン対、全画面ラジオ分岐(種別/即時/予約)、next/back以外の操作が無く背後にビューが無い閉じ込め。
3. reaction一覧を有向グラフ化: (a)入次数1/出次数1の一本道チェーン (b)「次へ/戻る」trigger比率 (c)collectionへ戻るエッジの無い「完了」終端 (d)decision frameのfan-out を抽出。健全形(collection⇄single双方向＋overlay→元ビュー復帰)から外れたエッジを列挙。**命名がオブジェクト名詞でもグラフが線形ウィザードなら不適合(命名は偽装可能、構造が正本)。**
4. 各objectでcollectionとsingle双方が存在し相互到達可能か(往復reactionが各1行立つか)を突合。片方欠落/片方向のみ(選択対象が次ビューに継承されない含む)は欠陥。
5. reaction未取得（1回目・§6配線前）なら「判定不能」(=適合ではない、空振り≠不在)。命名＋frame系列＋画面内mode固定UIの静的シグナルで暫定判定する（2回目の再監査は冒頭の発火規定どおり）。
6. **関係の双方向突合（表E）**: (a) 各frame内の他objectへの参照要素（関連一覧・参照リンク・パンくず・他objectのsingleへ向かうreaction）を全列挙し、表Eの行へ写像。写像先の無い参照=未宣言の関係→削除orエスカレ (b) 表Eの各行（`scope-out`を除く）が要素またはreactionエッジとして少なくとも1つ実在するか。無い=関係の欠落。reactionが要る判定は2回目のみ。
7. **操作権限の突合（表F）**: (a) 可否が「見るだけ/できない」の各行（`scope-out`を除く）について、そのロールの状態バリエframe（ロール別表示差・権限不足）上で当該操作の要素が非表示・無効化・権限不足状態のいずれかになっているか (b) ロール別表示差・権限不足の各frameが表Fの行へ写像されるか。「見るだけ/できない」行があるのにそのロールのframeが無い=状態欠落。
- **出力**: 「frame N件中 写像済みN / 未写像N」「線形チェーンエッジN件」「表E N行中 実在N / 欠落N・未宣言の参照N」「表F 制限行N件中 画面反映N / 未反映N」のカバレッジ形式・間引き禁止。違反0行でgreen。
- **proc:全件のリフレーム反証**: レビュアーが能動的にOOUI化を試み、候補object名指し＋失敗するドメイン制約を文書化。書けなければ proc:却下→OOUI化（→「手続き的フロー逃がし弁」）。

### ページ編成逆監査（§8(g) 詳細・実ファイル→宣言の双方向突合・間引き禁止）
0. 全Pageを実数取得で走査(`get_metadata`(nodeId無し)は1ページしか返らない罠を回避、空振りを不在と解さない)。各frameを実際の(object, view, state)に分類。
1. **散在検査**: 実ファイルから object→Page帰属集合を再構築し、|Page集合|>1 のオブジェクトを抽出。表Dで分割申告済み以外は違反→統合。
2. **孤立検査**: frame数=1のPageを全列挙。宣言で例外申告(横断Overview等)済み以外は違反。
3. **帰属/default-deny検査**: 実在するが宣言に無いPage/frame=スコープ膨張で弾く、宣言にあって不在=欠落で弾く(双方向)。
4. **横断検査**: 表Dの外向き配線の各to-frameが実在Pageに到達するか。別オブジェクトPageへの到達は正常(=横断)、同一オブジェクトのビュー割れは違反(=散在)。死配線/未配線を検出。
- **出力**: 違反frame/Page名のリスト。空であれば合格。差分が出たら配置を直すかマニフェストを更新して再監査。「散在していないはず」は不可、object→Page集合の実測でのみ合格。

### auto-layout厳守逆監査（§8(h) 詳細・実装→宣言・判定者は実装者と別個体＝§7敵対レビュー）
(g)ページ編成逆監査の直後に実行。§0表Bの『auto-layout既定＋abs:例外宣言』に対し、実装を構造で逆突合する（見た目でなく get_metadata の layoutMode/itemSpacing/padding/fills/strokes/children/layoutPositioning で判定）。

**検証はスクリプト＋手動走査の併走**: `~/.claude/skills/mikeneko-figma/scripts/audit-structure.js` を `use_figma` で実行する（F-STR-1/2・F-QLT-2/3・F-CMP-2 を機械検出）。ただし**スクリプトは ABSOLUTE 検査（下記手順4の検出シグナル5・6）と§0宣言との突合（下記手順5）を検査できない**（layoutPositioning を見ない・台帳突合は外側工程の責務）ため、スクリプトが green でも**手順4のシグナル5・6と手順5は常に手動で実行する**。スクリプト実行不可のときは手順1〜5の全部を手動 get_metadata 走査で回す。

1. `get_metadata` で実装済み全frameと全コンテナ(子2つ以上を持つノード)を実数列挙（`get_metadata`(nodeId無し)は1ページしか返さない罠を回避、全Page走査）。
2. 各コンテナを機械判定（**検出シグナル2: 非auto-layoutコンテナ＝手動配置**）: 子を2つ以上持つコンテナで `layoutMode==NONE`(またはlayoutModeプロパティ不在)、子がx/y絶対座標で並び間隔がitemSpacing/paddingでなく座標差で作られているものを列挙→§0でabs:宣言が無ければ違反。単一子のルート/キャンバス直下frameは除外。
3. 全ノードからSpacer候補を抽出（**検出シグナル1: 隙間専用空ノード＝Spacer本体**）: **(a)fills空 かつ (b)strokes空 かつ (c)子ノード0 かつ (d)非TextNode かつ (e)width or heightの一方だけ実寸(他方は0/極小 or 親方向にFILL)** を全件列挙。塗りも線も文字も中身も無く間隔だけ作る純粋な隙間ノード。誤検出ガード(後述)で除外し、残った無記名隙間ノードは違反。
4. auto-layoutコンテナの不一致・濫用を抽出し§0のabs:宣言と1:1突合（宣言外は違反）:
   - **検出シグナル3**: itemSpacing≒0 かつ padding≒0 なのに子の間に視覚的ギャップ＝ギャップが子側のダミー空ノードや固定sizeの透明子で作られている（itemSpacing/paddingと実測ギャップの不一致で検出）。
   - **検出シグナル4: 先頭/末尾ダミーによる擬似padding**: paddingLeft/Right/Top/Bottomが0で、代わりに端に塗り無し・文字無しの空ノードを置いて内側余白を作っている。
   - **検出シグナル5: layoutPositioning==ABSOLUTEの濫用**: 装飾(overlayバッジ/フォーカスリング)でない実コンテンツ・フロー参加要素がABSOLUTEで配置され、本来gap/paddingで並べるべき要素を絶対座標で逃げている。装飾(abs:宣言済み)以外のABSOLUTEを違反とする。
   - **検出シグナル6: 手動x/yによる間隔調整**: auto-layout子であるべき要素のx/yが、AL詰め後の期待座標(itemSpacing積算位置)からずれている＝overrideで手動ずらしして間隔を足している（absoluteBoundingBoxの実座標とAL理論座標の差分で検出）。
5. **§0宣言との突合**: abs:宣言した例外が(i)実在し(ii)逃がし弁の閉じたコードに該当し(iii)理由1行が反証可能か(「綺麗」「位置合わせが楽」「なんとなく」「AL組むのが面倒」は無効→差し戻し)を確認。**N突合は『ABSOLUTE/非AL配置として実装される宣言』に限り厳密に行う**（該当abs:宣言件数＝実装のABSOLUTE/非ALコンテナ件数。`abs:divider` 等paint持ちの通常auto-layout子として実装される宣言や `abs:test-canvas` 等の隔離Page宣言は件数突合の対象外とし、宣言どおりの実体〔paint有・隙間でなく線／隔離Pageに実在〕を個別確認する）。各abs:のリフレーム反証（レビュアーが能動的にgap/padding化を試み、失敗する構造制約を文書化。書けなければabs:却下→auto-layout化）を回す。
- **誤検出ガード（=違反にしないもの・機械的除外）**: ①空状態/プレースホルダ枠（空でもinstance実体・名前付きslot・将来コンテンツが入る宣言済み枠は正当。無記名の純空ノードのみSpacer判定） ②意図的divider（fill or strokeのpaintを持つRECTANGLE/LINEは区切り線であってSpacerでない＝塗り/線の有無が分岐点。ただし§構造系『場当たり線で取り繕わない』は別途適用） ③装飾overlay（abs:overlay-decor等で宣言済みのlayoutPositioning==ABSOLUTE） ④min/maxサイズ（コンテンツノードのminWidth/minHeightは隙間ノードでない）。これら4種は『塗り/文字/子/instance実体/宣言のいずれかを持つ』で機械的に除外し、純粋な無記名・無paint・無子の幅or高さだけノードのみをSpacer違反とする。
- **出力**: 『コンテナN件中 auto-layoutN/非ALN』『Spacer候補N件中 違反N/ガード除外N(各除外理由)』『ABSOLUTE/非AL対象のabs:宣言N=実装例外N・個別確認系(divider/test-canvas等)N件全確認』のカバレッジ形式（N突合の対象限定は手順5と同じ）。代表サンプル禁止・間引き禁止・全件列挙。**違反0行で初めてgreen**。違反が1件でも出たら修正(gap/paddingへ移行・Spacerノード削除・layoutMode付与)、ドメイン上どうしても非ALが要るならabs:でエスカレーション。§6配線とは独立に実行可。

## やってはいけない
- 規模クラス判定をせずに走り出す（往復数とチーム編成が決まらない）。
- 要件未確定・曖昧分岐が残ったまま手を動かす。
- 9項目テンプレを丸投げして個別承認を連鎖させる（規模に応じて束ねる）。
- 「作成フレームリスト／改修対象リスト／遷移配線リスト／ビューインベントリ／ページIA」を宣言せずに走り出す／リスト外を勝手に作る。
- 雰囲気で見出し・サブコピー・補足文・プレースホルダ・空状態テキスト・ヘルプ文を足す／「業界の典型はこう」で色・項目・要素を勝手に追加する（F-SRC-1/F-SRC-2/F-SRC-3違反）。
- 拡張候補リストに出典タグなしで項目を並べる／`guess:` を実装マッピング表に残す。
- 生hex／raw font-size／raw line-height／raw spacing／raw radius を置く（F-QLT-5・F-QLT-1違反。DS不在時の primitive 初回定義のみ例外）。
- 棚卸し不徹底のまま「無い」と断じて新規変数／新規コンポを作る。
- 既存DS部品を命名一致だけで採用する（用途違い事故）。
- 合成パターン（Table等）の内部欠落を「State A完全一致」で素通りする。
- 共有資産への追加を、ユーザー承認なしで行う。
- DS に実体がある部品を FRAME+TEXT で手描きする（F-CMP-2違反、必ず instance）。
- 要素を『画面固有レイアウト』と自己分類してF-CMP-5の分母から外す（分母はスタイル付き全ノード・自己認定不可）。
- **Spacerノード（無記名の無paint無子の幅/高さだけノード）を挟む／コンテナを layoutMode=NONE の手動配置で組む／間隔を abs座標・ダミーノードで作る**（F-STR-1/F-STR-2違反=auto-layout厳守違反、§8(h)で弾く）。例外は §0 で `abs:<code>` 宣言＋理由1行を取ったものだけ。
- `use_figma` のエラーを見逃して次の操作に進む。
- **プロトタイプ配線を省略する**／戻る導線をペアで宣言しない／状態保持遷移を単純Navigateで素通りする。
- 共通インスタンスの main 側に reaction を張る（全画面波及事故）。
- 改修対象リスト外の既存frameに「ついで」で変更を入れる。
- レビューを代表サンプル数件で済ます／繰り返しテンプレを全件突合の数に含めない。
- 未承認の保留事項を報告で隠す／暫定対応で埋めたことを黙る。
- **動詞/工程フレーム・step indicator・「次へ/戻る」主動線・全画面分岐選択を作る**（オブジェクトのビューに起こさずタスク/ウィザードに退行する＝鉄則13/F-OOUI-1/F-OOUI-2違反）。
- **種別/区分/貸出期間/返却期限をフレーム化する**（オブジェクトでなくプロパティ・状態・アクションに畳む＝F-OOUI-3違反）。
- **tagロンダリング**（ウィザードstepを「single・状態=作成中」と言い換えて逆監査を素通りさせる）。
- proc:逃がし弁を「綺麗」「ユーザーが期待」「作成フローだから」で正当化する（=書いたら差し戻し）。commit/handshakeの最小スパンを超えて、包むobjectの閲覧・編集ビューまで例外化する。
- **1画面=1ページで機能をばらまく（散在）／1frameだけの孤立Pageを連発する／ストーリー(業務フロー)単位でPageを切る**（F-PLC-4違反。フローは配線で表現、新規Pageは新オブジェクトのみ）。
- node-id指定があるのに新規Pageへ作る／「別ページ」依頼を同一Page内の新フレームで済ます（F-PLC-2違反）。
