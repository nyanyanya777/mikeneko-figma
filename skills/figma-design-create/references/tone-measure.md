# 実測（濃さ・太さ・線の強さ・余白）

**いつ読むか**: 工程1（見本を見るとき）と工程8（仕上げと判定の前）。`figma-ds-edit` で既存画面を刷新するとき、色・太さ・線・余白を直すときにも読む。

[figma-design-create](../SKILL.md) の詳しい手順。対応するルールは F-QLT-10（正典は [mikeneko-figma-rules](../../../skills/mikeneko-figma-rules/SKILL.md)）。

濃さ・太さ・線の強さは、見本を眺めて合わせたつもりになりやすい。面の色が見本と同じでも、線が数段濃い、選んでいない項目の文字が黒い、見出しが太字、というだけで画面全体が重く見える。値を取って並べれば、どこが違うかが分かる。

余白も同じで、変数に結びついていても、同じ種類のカードで内側余白が違う、14 と 16 が混ざる、行の高さが見本より詰まっている、ということは起きる。構造の監査（auto-layout か、変数か）は、値が合っているかまでは見ない。

## 1. 見本を決める

- 既存プロダクトの画面を作る・刷新するとき: 宣言した TWIN（F-QLT-7）が見本。
- 既存画面が無い新規サービスのとき: 依頼者が名指しした実在プロダクト。自分では決めない（候補を挙げて選んでもらうのはよい）。
- 見本は、成果物と同じ種類の画面で比べる（一覧なら一覧、ダッシュボードならダッシュボード）。

## 2. 見本を測る

- 見本が実アプリ・Webのとき: 実物をブラウザで開き、ライト表示・幅1440前後にして、[measure-reference.js](../../../skills/mikeneko-figma/scripts/measure-reference.js) を流す（読み取り専用）。
  - ログインが要る画面は、公開のデモか、依頼者が開いている画面で測る。開けなければ「測れなかった」と報告する。スクショから色を拾うのは、圧縮と拡大縮小で値がずれるので、実測の代わりにしない（使うなら「スクショからの概算」と明記する）。
- 見本が Figma の既存画面のとき: 見本のフレームにも [measure-tones.js](../../../skills/mikeneko-figma/scripts/measure-tones.js) を流す。
- **use_figma で流す計測は、承認のあとに行う。** measure-tones.js は読み取り専用だが use_figma で流すので、F-QLT-9 と F-CMP-7 では書き込みと同じに数えられる。Figma 上の見本と成果物の計測は、承認後（design-create では工程5の最初と工程8の判定の前。ds-edit では工程4の最初と工程6の判定の前）に行い、承認前の工程1では `get_metadata` と `get_screenshot` で見るだけにする。また、F-CMP-7 は「セッション最後の use_figma は run3」なので、計測は必ず run3 より前に済ませる。ブラウザで流す measure-reference.js はこの制約を受けないので、工程1で測ってよい。

## 3. 成果物を測る

- 成果物のフレームに [measure-tones.js](../../../skills/mikeneko-figma/scripts/measure-tones.js) を流す（読み取り専用）。面・線・文字が、色ごと・太さごとに件数つきで返る。各色がどの変数にバインドされているかも返る（`variable: null` は、変数に結びついていない値。生の値か、スタイル経由）。
- 同じ出力の `spacing` に、画面を組んでいる箱の内側余白と間隔が返る（部品の内側は数えない）。使われている値の一覧（`values`）、箱ごとの「上/右/下/左」（`boxes`）、変数に結びついていない段外れの値（`offScale`）、紛らわしい値の組（`nearPairs`。両方が変数の組は出ない）、同じ名前なのに余白が違う箱（`sameNameDiffer`）、左右や上下で余白が違う箱（`asymmetric`）。`heights` には、行（`rows`）と操作部品（`controls`）の高さが分かれて返る。どれも部品（インスタンス）の高さで、部品が決めている値（合わせ方は §6）。
- `offScale` は、バインド監査の前に見る下調べ用。変数に結びついていない余白の合否は、`audit-ds-binding.js` の BIND-SPACE が決める。監査の範囲に入っている箱については、監査を通ったあとは `offScale` が空になるのが正しい。計測は画面フレーム全体を測るので、監査の範囲の外（今回触っていない箱）にある既存の値は残る。それは、スコープ外の既知事項として報告する。4 の倍数かどうかで見るのは変数に結びついていない値だけなので、DS の spacing 変数（6 や 10 など）を使っている所は出ない。

## 4. 段階表にして並べる

同じ場所どうしを1行にする。半透明の色は、白地に重ねた実効色で比べる（measure-reference.js は `onWhite` で出す）。

| 場所 | 見本 | 成果物 | 差 |
|---|---|---|---|
| 面: アプリ枠（サイドバー）／本文／カード | | | |
| 線: 構造（面の境目・ヘッダーの下・カードの枠）／表の行／操作部品（ボタン・入力欄） | | | |
| 文字色: 主／副／補助／選んでいないナビ項目／アイコン | | | |
| 文字の太さ: ページ見出し／大きい数字／セクション見出し／本文／表の見出し行／ボタン／バッジ | | | |
| 塗り: 主ボタン／進み具合バー／濃いバッジ（明るさだけ比べる） | | | |
| 余白: 行の高さ／ナビ項目の高さ／操作部品の高さ／カードの内側余白／箱の間隔（よく使われている値）／サイドバーの幅 | | | |

見本の余白は measure-reference.js の `density`、成果物の余白は measure-tones.js の `spacing` と `heights` から取る。

## 5. どこを見るか

`figma-ds-edit` では、直すのは触った範囲だけ。計測は画面フレーム全体を測るので既存の不ぞろいも出るが、範囲の外は、スコープ外の既知事項として報告するにとどめる。

- **線は1色とは限らない。** 見本の線が段になっていることが多い（面の境目とカードの枠がいちばん薄く、表の行、操作部品の順に濃い）。成果物が全部同じグレーなら、構造の線が濃すぎる。
- **選んでいない項目の文字とアイコン。** 見本が副の色で置いている所を、成果物が主の色（黒）で置いていないか。
- **太字の有無。** 見本が太字をほとんど使っていないなら、差は大きさと色でつける。小さいバッジの文字だけ少し太い、という作りもある。
- **黒い塗り。** キットの既定のまま残った黒いボタン・黒い進み具合バー・黒いバッジが無いか（measure-tones.js の `darkFills`）。
- **表の見出し行。** 行と同じ色・同じ太さになっていないか。
- **密度。** 行の高さ、操作部品の高さ、カードの内側余白が、見本より詰まっていないか、空きすぎていないか。1か所だけでなく、全部が同じ方向にずれていることが多い。行と操作部品の高さは部品が決めているので、差があっても画面側では直さない（§6）。
- **同じ種類の箱の余白。** `sameNameDiffer` に出た箱は、意図した違いでなければそろえる。`nearPairs`（14 と 16 など）は、どちらかに寄せる。`offScale` は、その DS の spacing の段に乗せる。ただし、両方の値が DS の spacing 変数に結びついていて、見本（TWIN）でも同じ使い分けをしているなら直さず、理由を報告する（F-QLT-7）。計測の出力は見るための一次情報で、出たものを全部直せ、という意味ではない。
- **左右・上下の余白の違い。** `asymmetric` に出た箱は、意図したもの（アイコンの分だけ片側を詰める等）か、消し忘れかを1件ずつ見る。

## 6. 合わせ方

- 合わせるのは段階（何段あるか、各段の明るさ、太さの段、余白の段）。**色相・書体・ブランド色・角丸の形・画面の要素は写さない**（F-SRC-1。見本のタブや操作を足さない。他社の固有のデザインを再現しない）。見本が青みのグレーでも、自分のプロダクトの色相のまま明るさだけを合わせる。
- 合わせた値は変数として持つ（線の段、文字色の段、spacing の段）。余白は、見本の px をそのまま写さず、自分の DS の spacing の段のうち、いちばん近い段を当てる。既存の DS に段が足りなければ、変数の追加をエスカレーションする（新しい変数を無断で作らない＝design-create の鉄則5）。既存の変数の値を変えると既存の全画面に効くので、影響範囲を承認の票に書き、承認を取ってから変える。
- **部品が決めている大きさは、画面側で上書きしない。** 行の高さ、操作部品の高さ、部品の内側余白は、部品（メインコンポーネント）の値。見本と差があっても、画面側では合わせない。インスタンスの高さや内側余白をその画面だけ変えると、他の画面の同じ部品とずれる。生フレームで作り直すのは F-CMP-2 の違反、見た目を変えるためにメインコンポーネントをその場で編集するのは F-CMP-3 の違反になる（インスタンスの内側を生の値で上書きしない＝[ds](ds.md)「コンポーネント絡み」）。順に試す: (1) 部品に大きさの variant（size など）があれば、見本にいちばん近いものを選ぶ (2) 無ければ、差を段階表に残して、部品の改修として依頼者に相談する（[figma-component-design](../../../skills/figma-component-design/SKILL.md)。既存の使用箇所すべてに効くので、影響範囲を添える＝同スキルの鉄則12） (3) 改修しないと決まったら、「合わせなかった差」として報告する。画面側で合わせてよいのは、画面を組んでいる箱の余白（`spacing` に出る値）だけ。
- 文字を薄くしたら、コントラストを実測する（F-QLT-2。通常の文字は 4.5:1 以上）。
- 直し方は [build-method](build-method.md)「色や太さを後からまとめて直すとき」。

## 7. 確かめる

- 直す前と直したあとの描画を並べて見る。
- 面の境目など、狙った場所の画素の値を取る（`get_screenshot` で取った PNG を開き、境目をまたぐ数画素の色を読む）。
- **揃えを座標で測る。** 構造の値（padding、間隔）が合っていても、描画ではずれることがある（文字の上下の空き、中心に置いたつもりの要素のずれ、左右で違う内側余白）。レビューでは、次を数値で確かめる: (1) 同じ列に並ぶ要素の左端 (2) 中央ぞろえの要素の中心軸（ページや親の中心との差） (3) 兄弟どうしの間隔が等しいか (4) 箱の内側余白が左右・上下で等しいか（意図した違いを除く）。ずれは「どの要素が、何 px」で報告する。座標の取り方は次のどちらか。
  - `get_screenshot` の PNG から読む: 既定では長辺が 1024px に縮むので、`maxDimension` を元の幅以上にして取り、返ってくる `width` と `original_width` の比で Figma の px に換算する。PNG は返ってくる URL から落として読む。
  - `get_metadata` の位置と大きさから読む: 返る座標が絶対か親相対かを、初回に、位置の分かっているノードで確かめる。親相対なら、祖先の x/y を足して絶対座標にする。
  - 文字の上下の空き（文字そのものの見えている範囲）は、箱の座標では分からない。PNG の画素で測るか、use_figma で `absoluteRenderBounds` を読む（use_figma を使うなら run3 より前）。
- 判定役（F-QLT-6/7）に、成果物のスクショと一緒に、見本のスクショとこの段階表を渡す。

## 8. 報告に入れるもの

- 段階表（before→after）。余白の行を含む。
- 余白でそろえた箇所と、意図して残した違い（`sameNameDiffer`・`asymmetric` のうち直さなかったものと理由）。
- 合わせなかった差と、その理由（例: 操作部品の枠は見本のほうが濃いので変えていない）。
- 見本を測れなかった箇所。

実装を委譲するときのブリーフには、段階表の値（どの場所をどの値にするか）だけを書く。見本プロダクトの名前や画面は書かない（要素の出典と取り違えさせない＝F-SRC-1・F-PRC-11）。
