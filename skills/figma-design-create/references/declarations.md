# 要件の確定と宣言（表A〜F）

**いつ読むか**: 工程0で要件を1枚にまとめるとき、表A〜Fを書くときに読む。

[figma-design-create](../SKILL.md) の詳しい手順。工程番号（§0〜§9）は SKILL.md の標準オーダーの番号。ルールID（F-*）の正典は [mikeneko-figma-rules](../../../skills/mikeneko-figma-rules/SKILL.md)。

## 要件理解の手順（0 の中身）
着手前に以下を**1枚に書き出してユーザーに見せる**。**質問は規模クラスに応じて束ね**、未指定項目は最初のQ&Aに必ず含める。

### 必須項目（全規模共通）
- **画面の役割（1行）**: この画面で何が達成されるか。
- **画面サイズ・プラットフォーム・モード**: mobile（幅px）／web／responsive、light/dark対応の有無。
- **オブジェクトモデル＋OOUIビューインベントリ（表A/表B）**: 書く順は**表A（オブジェクト）→表E/表F（関係・操作権限）→表B（ビュー）**で、ビューは先に整えたオブジェクト・関係・操作権限から導く。作成フレームリストは**先にビューを確定してから導出する**。動詞・手続き・種別は表Aに畳み、独立objectにしない（この資料の「OOUIビューインベントリ」）。
- **ページIA宣言（表C frame帰属／表D Page構成）**: フレームをどのPageに配置するかを**オブジェクト単位**で宣言（この資料の「ページIA宣言」、[pages](pages.md)「ページ編成ガイド」）。新規Pageは新しいオブジェクトが登場するときだけ。
- **作成フレームリスト（新規）**: 今回新しく作る画面/フレームを全列挙（表Bから導出）。**状態バリエの有無**を§0段で宣言（「通常状態のみ」／「状態複数あり：詳細は§4で承認」）。複数ありなら§3マッピング表で全状態フレームを列挙し、§4で一括承認。
- **改修対象リスト（既存）**: 既存画面に追加・修正を入れるフレームを全列挙。改修分は [figma-ds-edit](../../../skills/figma-ds-edit/SKILL.md) に委譲。
- **派生・補助画面の見込み**: 入力→確認→完了 等の派生画面を仮置きし、要件時にユーザーに「この派生は要るか」を4択で問う。
- **遷移配線リスト**: from(画面/要素) → to(画面) のペアを全列挙。**戻る・キャンセル動線**も必ず明記。**1画面案件で配線が無い場合は「配線対象なし」と明示**。**画面間遷移は§0で全列挙、画面内状態間遷移（フィルタ結果0件→クリア→通常等）は§3マッピング表確定時に追加**（§0の段階で全状態×全遷移の積を埋めようとしない）。
- **表示項目／入力項目**: 既存呼称で。入力はラベル／任意・必須／選択肢／初期値まで。
- **使うべき既存パターン**: 既に存在する同種画面の参照（あれば node-id）。
- **曖昧分岐**: 自分で決められないところを箇条書きで列挙→ユーザーへ。

### OOUIビューインベントリ（表A/表B・委譲不可・§4承認対象）
書く順は 表A → 表E/表F（次節「オブジェクト関係・操作権限」）→ 表B。表Bは表A・E・Fから導き、作成フレームリストは表Bから導出する（先にビューを確定してからフレームを起こす）。

- 表A オブジェクト棚卸し（動詞・手続き・種別はここに書く＝独立objectにしない）:

  | object(名詞) | 定義1行 | 主要プロパティ・状態 | 主要動詞(=後でアクションchipになる) |
  |---|---|---|---|

- 表B ビュー割当（1frame=1行、view列はcollection/singleの二択）:

  | frame | object | view(collection\|single) | このビュー上のmodeless action chip(動詞) | 状態バリエ | 出典(req/existing:<nodeId>/ds) |
  |---|---|---|---|---|---|

**表B auto-layout既定（1行・全frame共通の既定値）**: 全frame及び主要コンテナはauto-layout(layoutMode=HORIZONTAL/VERTICAL)で組み、余白・間隔はgap(itemSpacing)とpaddingで制御、Spacerノード・非auto-layout手動配置・layoutPositioning=ABSOLUTEは既定で禁止=default-deny（**F-STR-1/F-STR-2 → [mikeneko-figma-rules](../../../skills/mikeneko-figma-rules/SKILL.md)§構造系が正典**）。既定から外す要素だけを、表Bの『出典』列（または§3マッピング表の該当要素行）に逃がし弁タグ `abs:<code>` を1つ付けて明示列挙し（[exceptions](exceptions.md)「auto-layout厳守の逃がし弁」）、各 `abs:` に『なぜgap/paddingでは表現できないか』の理由1行を必須化（無理由は差し戻し）。タグの無い要素は既定=auto-layout強制。列挙した `abs:` 例外は§4の一括承認に束ねる（出典タグ/proc:コードと同型で新しい宣言列は作らない）。

**宣言ルール**: ①全作成フレームは表Bに1行 ②view列はcollection/singleのみ ③collection/singleに収まらないframeは `proc:<code>` / `cross-object:` タグ＋理由を書き§4で個別承認（非object面は `proc:utility`）（default-deny、無宣言フレームは§8(f)で削除） ④動詞・種別・手続きはframe化せずA/Bに畳む ⑤表Bは表A・E・Fから導く——表Eの「画面上の現れ」に書いたframeはすべて表Bに行があり、表Fに「見るだけ/できない」行（`scope-out`を除く）を持つロールは、該当ビューの表B状態バリエ列に「ロール別表示差」か「権限不足」を持つ。

### オブジェクト関係・操作権限（表E/表F・委譲不可・§4承認対象）
表Aの各オブジェクトについて、他オブジェクトとの関係とロールごとの操作可否を宣言する（F-OOUI-6・F-OOUI-7 → [mikeneko-figma-rules](../../../skills/mikeneko-figma-rules/SKILL.md)§OOUI系が正典）。PRDがある案件は「8.3 関係」「8.4 多重度」「4.3 利用者×権限」をそのまま写し、ここで考え直さない。

- 表E オブジェクト関係（1関係=1行）:

  | from object | to object | 関係名 | 多重度(1:1\|1:N\|N:N) | 画面上の現れ(frame/要素: 関連一覧・参照リンク・パンくず等) | 出典(req/existing:<nodeId>/prd:§8.3) |
  |---|---|---|---|---|---|

- 表F 操作権限（1ロール×1object×1操作=1行）:

  | ロール | object | 操作(閲覧＋表Aの動詞) | 可否(できる\|見るだけ\|できない) | 画面上の現れ(表示/非表示/無効化/権限不足状態) | 出典(req/existing:<nodeId>/prd:§4.3) |
  |---|---|---|---|---|---|

**宣言ルール**: ①関係名・ロール名は利用者向け既存ラベル語彙（F-OOUI-1 PRIMEと同じ縛り）。出典の無い関係・ロールは作らず、ユーザーに1問で聞く ②関係を独立objectに昇格させない（F-OOUI-3） ③今回のframeに現れない行は画面上の現れ列に `scope-out` と書き§4で承認 ④表Aのobjectが1種類で他objectへの参照が0件なら表Eは「対象なし」1行、ロールが1種類なら表Fは「対象なし」1行。

### ページIA宣言（表C/表D・§4承認対象）
OOUIビューインベントリ表Bと1:1で連動させ、2表を出す:

- 表C frame帰属表:

  | frame | object | view(collection\|single\|sub) | state | 配置Page名(番号prefix付き) |
  |---|---|---|---|---|

- 表D Page構成表:

  | Page名(番号prefix) | 含むオブジェクト | frame数 | 外向き配線(→他Page frame) | 分割理由(あれば) |
  |---|---|---|---|---|

**宣言ルール**: ①1オブジェクト→原則1Page。分割する場合はプレフィックス共有(例「備品／一覧」「備品／詳細」)＋理由を明記 ②各Pageは最低2frame(孤立Page禁止。横断Overview等の例外は明示) ③ストーリー由来のPageは作らず配線で代替、通し閲覧が要るなら既存frameを複製せず参照を並べる薄い『フロー俯瞰』Page1枚に限定 ④ビューインベントリ表Bの各行がどのPageのどのframeに落ちるかを1:1で対応付け、新規Pageは宣言した新オブジェクトのみ許可。ユーザー承認なしに実装着手しない。

### データ操作系画面（L規模）の追加項目
ユーザーが「一覧」「管理」「ダッシュボード」「テーブル」等の語を含む依頼をしたら、以下を**領域別Q&Aで追加確認**:
- **データソース**: 何のデータ／レコード規模／ロード方式（一括 / 無限スクロール / ページネーション / カーソル）
- **ソート仕様**: 対象列／単一or複数キー／URL保持の要否
- **フィルタ仕様**: 単一/マルチ選択、AND/OR、即時/適用ボタン、URL保持、保存ビュー要否
- **状態網羅レベル**: 通常のみ／+空+エラー／+全網羅（[mapping](mapping.md)「状態バリエの分類別ホワイトリスト」）
- **ロール分岐**: admin/user/読み取り専用/担当者 等の表示差の有無
- **一括アクション**: 行選択・一括変更・削除等の要否
- **列カスタマイズ**: 表示列選択・並べ替え・幅調整の要否
- **エクスポート**: CSV／PDF 等の要否

### 曖昧指示の扱い（「よくあるやつ」「いい感じ」等）
9項目テンプレを丸投げしない。2点セットで確認:
1. **最小コア版**: 既存DS/既存画面で確実に出典が取れる項目だけで組んだ最小構成（例: 備品詳細なら 画像／備品名／保管場所／主CTA）。
2. **拡張候補リスト**: 出典が無く判断が割れる項目を **5〜8件**で箇条書き。**各候補に出典タグ必須**: `existing:<画面>` / `ds:<componentId>` / `similar:<参考機能>` / `guess:`（出典なし・推測）のいずれか。**`guess:` が3件以上を占めるなら、その時点でスコープ自体を要件主に確認するメタ質問**（「この画面は何が達成できれば完了か」）に切り替える。
