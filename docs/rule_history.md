# 共通ルール（F-*）の経緯

ルール本文は [mikeneko-figma-rules](../skills/mikeneko-figma-rules/SKILL.md) が唯一の正典です。このファイルは、本文を短くしたときに外した「なぜそのルールがあるか」をルールIDごとに残したものです。判断に迷ったときにだけ読みます。ここに書いてあることはルールではありません。事故例は架空のもの、または一般化した記述です。

## 体制
- **F-TEAM-0** もとは「このスキルを通る作業はすべて Workflow でエージェントチームを組む（小は5体未満、実装は figma-implementer）」だった。依頼者の指示「Figmaの作業とかには全部マストで入れてほしい」による。メインのモデルが Figma の実装に弱かった時期の決まりで、メインが最上位モデルで動くようになったため、規模3段に改めた（小・中はメインが直接、大だけチーム）。メインが最上位モデルでないときは従来どおり委譲する。[feedback_agent_team_delegate_all](./feedback_agent_team_delegate_all.md)

## 部品系
- **F-CMP-5** DS に Table が実在するのに、多数のノードを生で描いた。instance が1つも無い画面は、instance 実体監査が空振りして素通りする。それを防ぐためのルール。
- **F-CMP-6** あるプロダクトで、サイドバーの生フレームの複製クラスタが複数あり、全ゲートが GREEN のまま素通りした。
- **F-CMP-7** 生フレームは「見た目が正しく出る」ので視覚ゲートを素通りする（事故3件に共通の機序）。散文で必須にしても止まらなかったため、Stopフックで実行の痕跡を照合する形にした。
- **F-PRC-12** 逃げ場を書式から消した結果、実運用では `reuse:<node-id> (raw:<コード>)` と正規の票に弁明を埋め込む形で回避され、書式は通るが実態は生フレームになっていた。塞ぐのでなく、正面の票（raw）にして見えるようにする方針へ変えた。もとの事故は、入口スキルは通したが作業スキルをロードせず、実装ワーカーが DS の存在を知らないまま生フレームで組んだこと。

## 配置系
- **F-PLC-5** 「同じページに複製」の指示に対し、get_metadata の一覧に出た唯一のページ（実際は無関係な別ページ）に複製が作られ、依頼者の指摘で発覚した。原因は未確証だが、現象は実測で再現している（複数ページのうち1ページしか一覧に出ず、複製がそのページに作られた）。
- **F-PLC-6** この規約自体が事後承認で成立した。「軽微だから自己判断で省く」を防ぐために明文化した。

## 出典系
- **F-SRC-1** 「良かれと思って足す」は本人には違反に見えず、自制では止まらない。そのため意図でなく出典で縛る。依頼者の逐語「項目とかは僕が決めるから、やめて勝手に作るのは。」「一覧画面で勝手にタブ変えてたり、何か必要ない編集機能出せたりしてるよ」、AskUserQuestion の回答「議事録の項目は置いてよい」。事故: 設計書の同じ行に「並び替えのタブ化は brief」由来の要素と existing が同居していた。別の設計書でも、サイドパネルの追加タブが既定の保管場所の existing と同じ行に REF で入っていた。
- **F-SRC-2** 備品貸出アプリ（架空の例）の項目を、無関係な会員登録に足した類。ロードされた他案件の記憶は背景情報であって出典ではない。
- **F-SRC-4** 「返却ボックス/代理返却」を「該当フレームに無い」だけで削り、網羅落ちになった。代理のシグナルを一次の出典（依頼者の逐語）より上に置いた削除は、破壊系の事故。

## OOUI系
- **F-OOUI-1〜8** 「OOUIで作れ」という意図ベースの指示は効かない（生成時に自分を正当化済みで、違反が見えない）。出典ゲートと同じ「宣言→機械的な逆監査」で縛る。
- **F-OOUI-4** 段と一緒に返却ボックス・代理返却を削り、窓口1本にしてしまった。[feedback_keep_stated_core_verify_fully](./feedback_keep_stated_core_verify_fully.md)
- **F-OOUI-8** 備品貸出アプリ（架空の例）で、洗い出した200件超の概念をそのまま箱にし、状態の値（貸出可・修理中など）や操作まで別々のオブジェクトとして並べた。OOUIの型で畳み直すと、オブジェクトは備品・予約・貸出履歴などの一桁に収まり、残りは対応表でプロパティ・アクションに割り当てられた。

## 品質系
- **F-QLT-6** ある画面（架空の例、備品貸出アプリの備品詳細）を「DS規約順守タスク」として委譲した。変数バインド・AA・OOUI が全緑、レビュー致命0で合格印を押したが、白カード＋細いグレー線＋中立色の平坦なワイヤー止まりで、依頼者に却下された。
- **F-QLT-7** 同じ画面を別プロダクトのDSファイル単独で起こし、既存の備品一覧／予約ダイアログの視覚言語（色の使い方・カードの質感）とかけ離れた画面を出して却下された。「ワイヤーを脱する」名目で派手な device を足すのは典型的な失敗。
- **F-QLT-8** もとは全作業で必須、lazyweb が不通なら完了不可（fail-closed）だった。規模3段に改めたとき、大のときと依頼者が求めたときだけに絞り、不通時は「未実施」と報告して依頼者の判断を仰ぐ形にした。report を判定役に再判定させないのは、コストが約15倍になるため。
- **F-QLT-9** 見た目の完成度が判定対象の案件で、レビューを2回とも Sonnet で回し、Fable に一度も見せないまま進んだ。散文としては既に必須だったが止まらなかったので、Stopフックにした。きっかけを「判定が要る案件か」の自己申告でなく「書き込みを呼んだか」の機械検出にしたのは、自己申告だと毎回そこが飛ぶため。書き込みの検出をサブエージェント内まで数えるのは、Figma の書き込みを委譲する運用で検出漏れになるため。
- **F-QLT-10** 製品画面の濃さを、依頼者に2回「濃すぎる」と言われた。面の色は見本とほぼ同じで、原因は線（見本より10段ほど濃い）と、選んでいない項目の文字色・太さだった。見本を眺めて合わせたつもりでは気づけず、実物の値を取って並べて初めて分かった。 余白も同じで、同じ案件のメインビジュアル案では、左右の箱の内側余白の違い（32 と 44）とボタンの中心のずれ（10px）が、別のエージェントが描画から座標を測って初めて見つかった。構造の監査（auto-layout か、変数に結びついているか）は、値が合っているかまでは見ない。そのため、余白も計測の対象に足し、揃えは座標で測ることにした。 見本の密度（行の高さ、操作部品の高さ）は部品が決めている値なので、「見本に合わせる」を画面側の上書きで行うと、部品の実体のルール（F-CMP-2・3）とぶつかる。そこで、部品が決める大きさは variant の選び直しか部品の改修で扱う、と決めた。段外れの値（`offScale`）は、既存のバインド監査（BIND-SPACE）と重なるので、監査の前の下調べ用とした。

## 進め方系
- **F-PRC-5** あるプロダクトで「全コンポーネントにバインド」の goal を、作業中の1ページだけ監査して完了報告した。キットの別ページの Input 等が丸ごと未バインドで、網羅漏れになった。
- **F-PRC-6** 同じ件で複数回、node-id つき URL（node 123:456="Content"）を一度はファイル/ページ全体へ広げ、次は逆に1フレームへ狭め、両方向で判定を誤った。動詞の丁寧さで網羅へ広げるのが事故の抜け道だった。
- **F-PRC-7** figma-implementer に `model:"sonnet"` を渡して Opus から Sonnet に格下げし、接地の悪いブリーフと相まって、実アプリと別物の劣化した出力になった。視覚階層・既存言語への適合・レイアウトの判断は、モデルの地力が直接効く。
- **F-PRC-11** あとの改定で、(1) 画面・フローは「サービス段→UIパターン段」の二段にした (2) REF は見た目と配置の参考だけで、要素の出典にならないと明記した（F-SRC-1）。規模3段に改めたとき、中・大で新しい見た目の判断を伴うときだけに絞った。

- **F-PRC-13** ある案件で、最初から同じ材料を持っていたのに、最初の数案はどれも却下された。出来が上がったのは、依頼者の短い却下（「線っぽいのはだめ」「AIすぎる」など）が無難な型を1つずつ消したから。こうした好みと禁止は、着手前に聞いても出てこず、何かを見せたあとに出てくる。また、会話が長くなって要約が入ると、途中で決まったことは要約に残った分しか引き継がれなかった。そのため、言われた言葉のままファイルに残し、毎回最初に読む形にした。
- **F-PRC-14** 同じ案件で、方向が変わったのは毎回、依頼者が画面を見て数分で言った一言だった。表や宣言を先に全部固めても、ここは拾えない。代表の1画面を先に見せれば、残りの画面を作る前に方向の違いが分かる。
