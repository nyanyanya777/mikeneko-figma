入口SOTの **F-CMP-7**（3runの実行表）が「何をやるか」の正本。ここはその**機序と限界**＝実行手順に要らないが、詰まったとき/改修するときに要る情報。配線の全体像は `reference_figma_component_gate_wiring`。

**なぜ3runに分かれるか**
- F-CMP-5（生フレーム）は各ノード単独で判定できるので、**成果物スコープ**で測れる。ページ全体で測ると着手前から在る既存負債で必ず落ち、通すために免除語彙へ逃げる圧力が生まれる（＝ゲートが死ぬ経路）。
- F-CMP-6（複製）は「走査範囲内に同一シグネチャが2件以上」でしか立たない。新規ノードだけを渡すと**典型ケース（既存1件＋今回作った複製1件）が原理的に検出不能**なので、比較相手を含む範囲で別途測る。よって合否も `cmp:0` では判定できない（既存負債があれば必ず cmp>0）。
- 突合キーが「配下かどうか」なのは、クラスタが返すのが**任意の深さの子孫frameのid**で、自分が作成/置換したルートidとは通常一致しないため。id一致で照合すると「既存カード1件×今回作った画面の内部カード1件」が素通りする。**id接頭辞は作成セッション由来で階層を保証しない**ので祖先関係の根拠にならない。
- 親辿りrunは監査署名（`auditStructure|F-CMP-AUDIT`）を含まないので**audit-only自動免除の対象外**（免除は「全ての書込が監査スクリプト」のセッション限定＝実装セッションでは元々成立しない）。
- 順序が要件なのは、Stopフックが「**最後の書込以降**にpass行があるか」で判定するため。run1/run2で終えると中身が全部合格でも構造的にBLOCKする。

**実装の細部**
- クラスタメンバーidの入手元は violation の `detail` 文字列の「出現位置: 」以降（構造化配列ではないのでパースが要る）。
- 「1回目runの走査id集合と突合」は**できない**（スクリプトは `scanned:` の件数しか返さずid一覧を持たない）。将来 summary に `dupmine:<N>` を足せば配下判定を機械化できる＝未実装。
- summary の `roots:` は実効ルート（`stats.rootIds`）から生成。30件超は先頭30件＋`,+N-more` に丸める。
- violations は**ルール優先度順**（F-CMP-6→F-CMP-5→F-QLT-5→…）で60件cap。発見順capだと件数の多いF-QLT-3/2が枠を食い、複製が1件も返らない。

**既知の限界（実測済み・違反は一次情報であって判決ではない）**
①親名を変えた複製はシグネチャが逃げて未検出 ②RECTANGLE複製はF-CMP-6の対象外 ③孫を見ない浅いシグネチャなので、直下children構成が同じで中身が違う複製を誤検出し得る。→ 該当ノードを開いて実際に同一か確認してから2コピー則を適用する。

**事故記録（いずれも実測で発覚）**
- レガシーファイル（数千ノードのファイル）でページ全体を測ると `cmp` が0にならず。内訳は全て着手前から在る画面ルートframeのfillで、成果物由来はゼロだった＝測定範囲を分けるきっかけ。
- 条文が「親辿りrunはaudit-onlyで自動通過」「1回目runの走査id集合と突合」と書いていたが、どちらも実行不能だった（フックはAND条件の第1条件で落ちる／スクリプトはid一覧を返さない）。**条文がフック実装の内部仕様を二重簿記していたのが原因**——スクリプト改修5回に条文改稿6回が随伴した。減らすべきは機構ではなく、機構を散文で写した鏡像（Fable所見）。

**改修時の注意**: このゲートは条文・スクリプト・フックの3点が噛み合って初めて成立する。条文だけ直しても実挙動は変わらないし、その逆も同じ。回帰スイートは `~/.claude/jobs/` の `audit-harness/`（オフライン16ケース）と `hook-tests/`（合成トランスクリプト）を使い回す（恒久配置は未了）。
