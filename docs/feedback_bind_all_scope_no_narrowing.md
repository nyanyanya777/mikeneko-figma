ユーザーが「すべてのコンポーネントにバインド」等、対象を**すべて/全部/全ページ**で明示したら、それは**ファイル全体（全ページの全コンポーネント）が対象**。直前まで作業していた1ページ/サブセットに勝手に狭めてはいけない。

**Why:** 「すべて」は逐語SOT（`feedback_verify_intent_before_scaling`）。安い方向へ縮めた解釈は、納品先（クライアント）での網羅漏れ＝**ユーザーの評価毀損**に直結する。1ページ緑は代理指標（[feedback_qa_real_user_outcome](../docs/feedback_qa_real_user_outcome.md)）。

**How to apply:**
- ①"すべて/全部/全ページ"を含む指示は、対象＝ファイル全ページ（or 明示された全範囲）と解釈する。狭めたいなら着手前に「対象は◯◯ページ群でよいか」を理由付きで明示確認（スコープ質問を"次元"だけに限定して"ページ範囲"を確認しないのはNG）。
- ②完了前の全数監査は**全ページ loadAsync してページ横断**で取る（off-pageマスターのインスタンス子は未ロードだと列挙漏れ＝件数が揺れる。1ページ走査で loose 0 だから完了、にしない）。
- ③完了宣言前に「宣言範囲の全ページ集合 vs 実際に処理したページ集合」を双方向diff。`feedback_operationalize_goal_before_building` [feedback_figma_url_scope_page_vs_file](../docs/feedback_figma_url_scope_page_vs_file.md)

**事故（架空の例、レシピ共有アプリ ヘッダー統一）:** 逐語「ヘッダーの挙動を変えて。**全ての画面で**」に対し、主要4画面（ホーム/検索結果/レシピ詳細/投稿フォーム）だけ修正して完了扱いにし、残りの画面には**デザイン的正当化の顔をした無承認例外**を委譲ブリーフに入れた。以後ユーザーが「ここだけヘッダー違う」と同趣旨を何度も指摘したのに、自分の例外設計を正とみなし別要因の説明を繰り返し、誤方向の修正を2回マージ。「何回言えばわかるの」まで発展。教訓: (1)全称指示への例外は肯定文の顔（「〜では非表示」）でも否定制約＝出典必須。(2)同種の表示/挙動指摘が2回目に来たら、環境要因を主張する前に「自分のブリーフ×ユーザー逐語のspec-diff」を先に取る（過去の自分のローカル解釈は新逐語の下位）。(3)コード文脈でも本ルールは同強度で適用。

**事故（架空の例、備品貸出アプリ DS）:** goal「すべてのコンポーネントにバインド」に対し、作業中の「ユーティリティコンポーネント」1ページだけを監査して loose0・完了と報告。ユーザーはキットのInput等**別ページのコンポーネントが丸ごと未バインド**なのを見て「全く満たしてない・ちゃんと範囲区切ったよね」と激怒。スコープ確認質問も"次元(fill/radius…)"だけ聞いて"ページ範囲"を確認せず、安い方（1ページ）へ自己解釈で縮めたのが原因。スキル入口 F-PRC-5 に規則化。
