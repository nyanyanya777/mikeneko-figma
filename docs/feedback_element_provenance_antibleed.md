AIが「良かれと思って」要件にない要素を足す／他サービスの要素を混ぜる（架空の例: レシピ共有アプリの「投稿者に呼んでほしいニックネーム」欄を無関係な会員登録に足す）のを止めたい、というユーザー依頼への設計解。

**メタ原則（これが肝）:** 「勝手に足すな」という意図ベースの禁止は効かない。生成時、AIは各要素を正当化済みで、自分が違反していると認識できない（違反が透明）。だから**実行者と認識を共有しない第三者が機械的にチェックできる形＝出典ベースのゲート**に置き換える。

**4点セット（mikeneko-figma入口＋design-create/ds-editに実装済み）:**
1. 全要素は出典必須（default-deny）。各フィールド/要素は (a)要件 / (b)“このサービス”の参照画面nodeId / (c)DS既定・機能必須ホワイトリスト のどれかに辿れること。辿れない要素は置かない。「指定されたフィールドが全て、それ以外は無い」を既定に。
2. アンチブリード：記憶・文脈・別プロジェクトの要素は出典にならない（背景情報であってソースでない）。別サービスの同種画面から写すのは guess 扱い＝本実装不可。
3. 「良かれ」は行動でなく提案へ逃がす。勝手に置かず拡張候補リスト（guess）に積んで承認を取る。抑圧は効かないがリダイレクトは効く。
4. 最終ゲートで逆差分監査（実装→宣言）：実装に存在する全要素を列挙し、§0/§3の宣言に無い要素が出ていたら削除かエスカレーション。**※既存物の改修では双方向にする**＝実装→宣言（余分な追加を消す）に加え、**基線→実装（改修前の現物にあった項目が落ちていないか）**も突合。改修は出典(a)(b)(c)に加え**(d)改修前の現物スキーマ**を第一SOTに置く。追加だけ守り既存の温存を守らない非対称が事故る（`feedback_schema_refit_baseline_sot`）。

**Why:** 失敗は2病理（良かれによるスコープ膨張＋記憶注入由来の文脈ブリード）。両方とも「本人から見て違反が透明」が根。出典必須＋逆差分なら検証可能。

**How to apply:** `feedback_figma_no_spacer_iconbutton`の共通禁止事項群と同じ系統。コピー出典タグ(`feedback_no_template_stock_phrases`/design-createの6分類)を要素レベルへ拡張したもの。[feedback_verify_absence_before_creating](../docs/feedback_verify_absence_before_creating.md)（重複作成NG）と対。図以外の生成タスクにも転用可。
